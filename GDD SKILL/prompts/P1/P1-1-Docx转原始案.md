## 提示词正文（复制以下内容）

```
【规格交付 · Part 2 · 入口】
将策划提供的策划案源材料规范化为标准「01 原始策划案」，作为后续 P2/P3 的统一输入。
保留全部业务信息；不得概括删减；不得写 R/P 编号（那是 P2 的工作）。

功能名：{功能名}
feature_root：产出/{功能名}

【@ 必读输入】
- 源文档/{策划案}.docx（或 .md / 口述整理稿 / 原始策划案-草稿.md）

【本步任务】
整理为规范的「01 原始策划案」定稿。

【输出路径】
{feature_root}/01-原始策划案/{功能名}/原始策划案.md

【本步格式要求 — 必须包含六章节】
1. 概述（玩法说明、设计目的、文档范围）
2. 功能流程（主流程 ASCII/文字、关键子流程）
3. 规则（基本规则、各子系统规则、特殊规则）
4. UI及交互（入口、各界面：布局→交互→身份/阶段差异→空态）
5. 美术需求（Icon、背景、动画，带编号）
6. 配置结构（Const 常量、配置表清单与字段说明）

边界标注（必须）：**继承现网** / **本次新增** / **本次改动**

【Part 2 公共铁律】
1. 自然语言叙述，讲清楚设计意图
2. 不确定处标「【待确认】」，不留空壳章节
3. docx 提取稿须保留表格（转 markdown 表格）

【本步铁律】
- 不要输出 R-xxx / P-xx 编号
- 不要写伪代码和服务端实现细节
- 不要拆成 8 维度文件夹

【完成后自检】
- [ ] 六个章节是否都有实质内容？
- [ ] 继承现网边界是否说清？

请直接写入 原始策划案.md，不要只输出大纲。
```
