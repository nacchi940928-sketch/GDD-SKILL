# P2 需求拆解 — 维度规范（Skill）

> **本文件是 Skill（知识与规范）**，不是提示词。  
> 执行拆解请使用 `prompts/P2/P2-*.md` 中的提示词。

---

## 定位

**`02-需求拆解.md` = 策划/运营/产品/老板汇报文档**，用自然语言写清「做什么、什么时候、玩家看到什么」。

程序实现规格（伪代码、P-xx、协议、配置表、审计）在 **P3 → `03-功能点梳理.md`**，不在 02。

写作规范：[templates/02-需求拆解-写作规范.md](../../../templates/02-需求拆解-写作规范.md)

---

## 公共铁律

0. **路径**：产出写在 `产出/{功能名}/`；合并为 **`{feature_root}/02-03需求拆解与功能点梳理/02-需求拆解.md`**
1. 每条有唯一编号（R-/EX-/T- 等），标注来源章节（01）
2. **自然语言优先**：规则写「规则说明」段落，不写伪代码、不写 P-xx 读写表
3. 与 L1 相同处写「继承 {skill_id}」，只写 delta
4. 禁止「见原始文档」；禁止把 03 才该有的实现细节堆进 02
5. **P-xx 不在 02 登记**：字段映射、配置表、协议 → **P3-3 / 03 附录 A**（P2-DS 改为产出「数据概要」文字）
6. 状态机用**玩家/界面视角**阶段名，不用服务端枚举作主标题
7. **数据契约、全量审计、校验 V-xx 表** → 03，不在 02

## 职能分轨

| 内容 | 02 写法 | 03 对应 |
|------|---------|---------|
| 业务规则 | R- 自然语言 | 怎么实现 + 伪代码 |
| 边界/异常 | EX-/PRE-/LIM- 用户语言 | 协议失败码 + 校验 |
| 界面跳转 | UI 交互（策划视角） | 模块 + 数据来源 |
| 流程 | 单局/活动日程 | Phase 状态机 |
| 测试 | T-/B-/E- 操作步骤 | 附录 B 细场景 |
| 协议/字段/表 | **仅数据概要** | 附录 A/D + 配置表 |

## 维度索引

| 维度 | 编号 | Prompt | 02 产出要点 |
|------|------|--------|--------------|
| 规则 | R- | P2-R | 规则说明段落，无伪代码 |
| 边界条件 | EX-/PRE-/LIM- | P2-EX | 用户可感知的前置/异常 |
| 红点 | RD- | P2-RD | 出现/消失（界面位置），少写字段 |
| 数据源 | — | P2-DS | **§6 数据概要**（表名列表），非 P-xx 索引 |
| UI交互 | — | P2-UI | 跳转、HUD 行为 |
| 状态机 | — | P2-SM | 玩家流程，非 LOBBY/MATCHING 表 |
| 校验规则 | V- | P2-V | 02 可省略；详细 V-xx → **03** |
| 验收标准 | T-/B-/E- | P2-T | 用户操作语言 |

## 规则维度格式示例（02）

```markdown
## R-{缩写}-001 段位优先匹配

**规则说明**：玩家确认角色并点击匹配后，系统优先在同段位队列中寻找对手并加入等待；若同段等待时间过长，再按规则逐步放宽段位范围直至组局成功或玩家取消。

【待确认】放宽等待的具体秒数、房间人数上下限。

**来源**: 01 §2.1
```

## P2 与 P3 衔接

P2 完成后，P3 **必须**从 02 的 R-/流程/UI **展开**为可开发规格：

- 每条 R- → 03「怎么实现」伪代码 + P-xx
- 02 §6 数据概要 → 03 附录 A + 配置表 + 协议
- implementation_data 审计 → **03 附录 D**（非 02）
