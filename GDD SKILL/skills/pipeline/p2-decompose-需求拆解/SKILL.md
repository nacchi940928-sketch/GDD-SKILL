# 需求拆解 — 维度规范（Skill）

> **目录**：`p2-decompose-需求拆解/` · **文档阶段**：02  
> **本文件是 Skill（知识与规范）**，不是提示词。  
> 执行拆解请使用 `prompts/需求拆解/` 中的提示词。

---

## 定位

**`02-需求拆解.md` = 策划/运营/产品/老板汇报文档**，用自然语言写清「做什么、什么时候、玩家看到什么」。

程序实现规格（伪代码、P-xx、协议、配置表、审计）在 **功能点梳理 → `03-功能点梳理.md`**，不在 02。

写作规范：[templates/02-需求拆解-写作规范.md](../../templates/02-需求拆解-写作规范.md)

---

## 公共铁律

0. **路径**：产出写在 `产出/{功能名}/`；合并为 **`{feature_root}/02-03需求拆解与功能点梳理/02-需求拆解.md`**
1. 每条有唯一编号（R-/EX-/T- 等），标注来源章节（01）
2. **规则边界**：每条核心 R- 须标注 **边界**（`继承现网` / `本次新增` / `本次改动`），与 01 边界标注一致，写在 §3 规则条目中（不单独立章）
3. **自然语言优先**：规则写「规则说明」段落，不写伪代码、不写 P-xx 读写表
4. 与 L1 相同处写「继承 {skill_id}」，只写 delta
5. 禁止「见原始文档」；禁止把 03 才该有的实现细节堆进 02
6. **P-xx 不在 02 登记**：字段映射、配置表、协议 → **功能点梳理·字段映射 / 03 附录 A**（需求拆解·数据源 改为产出「数据概要」文字）
7. 状态机用**玩家/界面视角**阶段名，不用服务端枚举作主标题
8. **数据契约、全量审计、校验 V-xx 表** → 03，不在 02
9. **歧义消歧**：01 若同时出现「轮流/同时/并行/依次」等矛盾表述，02 须在规则或 §2 中**择一**写清，并注明来源或【待确认】
10. **终裁归属**：凡先到先得、排序、计时截止类规则，须写清「由谁终裁」（如：权威方收包顺序 / 配置表驱动 / 【待确认】）；禁止无依据默认客户端终裁
11. **对称规则**：01 存在成对特殊规则（如 A 触发全员 0 分）时，须检查对称规则是否存在；有则同写或同标【待确认】

```markdown
| 编号 | 内容子类 | 策划定义 | 数量级 | 配置/数据来源 | 关联规则 | 关联 UI | 边界 |

```

## 规则维度格式示例（02）

```markdown
## R-{缩写}-001 段位优先匹配

**边界**：本次改动 · 匹配系统（放宽段位策略相对现网调整）

**规则说明**：玩家确认角色并点击匹配后，系统优先在同段位队列中寻找对手并加入等待；若同段等待时间过长，再按规则逐步放宽段位范围直至组局成功或玩家取消。

【待确认】放宽等待的具体秒数、房间人数上下限。

**来源**: 01 §2.1
```

## 需求拆解 与 功能点梳理 衔接

需求拆解 完成后，功能点梳理 **必须**从 02 的 R-/流程/UI **展开**为可开发规格：

- 每条 R- → 03「怎么实现」伪代码 + P-xx
- 02 §1.5 CNT- → 03 可按系统/内容类分批展开
- 02 §6 数据概要 → 03 附录 A + 配置表 + 协议
- implementation_data 审计 → **03 附录 D**（非 02）

## 需求拆解 完成门禁

- [ ] 九步内容已合并进 **`02-需求拆解.md`**（含 §1.5；纯流程包可注明无新增 CNT）
- [ ] 策划可读：全文无伪代码块、无 P-xx 大表、无数据契约审计节
- [ ] §1.5 各系统**子类**是否齐全（与 01 / §6 对齐）？
- [ ] 核心 R- 均有「规则说明」+ 来源
- [ ] 核心 R- 均已标注 **边界**（继承现网 / 新增 / 改动）
- [ ] §6 仅为数据概要，并指向 03
- [ ] 阻塞项已登记 Q-D / Q-R → `04/` 与看板
- [ ] **03 尚未写全时**，02 不得标「可开发」——可开发以 03+附录为准
- [ ] §1 含 **做/不做** 范围表（无明确「不做」时第二列填【待确认】）
- [ ] §2 各阶段含 **阶段内状态**（能否移动、倒计时是否等满、能否放弃/跳过）
- [ ] 竞争/排序类 R- 已写 **终裁方** 或【待确认】
