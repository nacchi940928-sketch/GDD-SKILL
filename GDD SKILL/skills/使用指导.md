## 0. 两种跑法（整包 vs 半自动）

Part 2 规格交付有两种常用方式，选其一即可。

### 方式 A：Cursor 一键编排（最接近整包输出）

在 Cursor 对话里 **@ docx 或 01**，并说明按 **`gdd-decompose`** 执行。Agent 会按 [`gdd-decompose/`](gdd-decompose/SKILL.md) 与 [reference.md](gdd-decompose/reference.md) 自动选阶段、逐步读 `prompts/` 里的 Prompt、写入 `产出/{功能名}/`。

**示例（docx → 03）**：

```text
@GDD SKILL/源文档/{你的策划案}.docx
工作包：{功能名}
请按 gdd-decompose 整包拆解，从 docx 跑到 03 完成，feature_root=产出/{功能名}
```

**01 已定稿时**：

```text
@GDD SKILL/产出/{功能名}/01-原始策划案/{功能名}/原始策划案.md
工作包：{功能名}，按 gdd-decompose 从需求拆解跑到 03
```

| 你说… | 跑到哪 |
|--------|--------|
| 整包 / 全流程 / 拆到 03 | 当前入口 → 03 完成（04 清单可选） |
| 拆到编译 / compile | 含 P4～P5，执行 `compile.py` |
| 只拆 02 / 需求拆解 | 需求拆解 9 步 |
| 只拆 03 / 功能点梳理 | 功能点梳理 6 步 |
| 继续 / 全流程 / 不要停 | 连续执行，不在每步暂停 |

默认**一步一确认**；要说「不要停」才会连跑。编排细节见 gdd-decompose Skill，不必手动翻各步 Prompt。

**拆解完成后不要自动跑规范反哺** — 见 [§0.1 双轨工作流](#01-双轨工作流交付-vs-演进)。

### 方式 B：半自动（不用 Cursor Skill）

不依赖 gdd-decompose 时，打开 **[prompts/规格交付库.md](prompts/规格交付库.md)**，按 **§4 推荐顺序**逐步操作：

1. 打开对应阶段的 `.md`（如 `prompts/需求拆解/规则.md`）
2. **仅复制**「提示词正文」代码块（不含文末「输入内容示例」）
3. 替换 `{功能名}` 等占位符，按 Prompt 内「@ 必读输入」引用文件
4. 本步自检通过后，再进下一步

单步路径、对话示例、@ 写法见 [§6](#6-详细使用说明)。**一次对话建议只跑 1 个 Prompt 步骤**（功能点梳理·功能点拆分 可按章节分批）。

## 0.1 双轨工作流（交付 vs 演进）

| 轨道 | Cursor Skill | 改什么 | 何时跑 |
|------|--------------|--------|--------|
| **A 交付** | `gdd-decompose` | 仅 `产出/{功能名}/`（01～04、logs、三包） | @ docx 或 01，跑拆解 |
| **B 演进** | `gdd-norm-feedback` | 仅 `产出/…/规范反哺报告.md`（**建议**，不改库） | **维护者显式要求**时另开会话 |

```text
轨道 A：docx → P1～P3（→ P4～P5）→ L2 交付物
              ↓（不自动）
轨道 B：维护者说「规范反哺」→ 规范反哺报告.md → 人工审阅 → 另会话改 prompts/skills（S1～S7）
```

**禁止**：在 gdd-decompose 整包跑完后**自动**进入规范反哺或改 `prompts/`、`skills/`，避免规范库反复替换。

规范反哺示例（**单独对话**）：

```text
@GDD SKILL/产出/{功能名}/02-03需求拆解与功能点梳理/02-需求拆解.md
@GDD SKILL/产出/{功能名}/02-03需求拆解与功能点梳理/03-功能点梳理.md
@GDD SKILL/产出/{功能名}/logs/

请按 gdd-norm-feedback 生成规范反哺报告；不要改 prompts 和 skills。
```

详见 [prompts/规范反哺/README.md](prompts/规范反哺/README.md) · [P2-P3-待完善清单.md](P2-P3-待完善清单.md)

## 1. 目录分工（不要混用）

| 目录 | 角色 | 谁写 | 是否进 Git |
|------|------|------|------------|
| **`源文档/`** | **策划 docx 归档**（可选，**不纳入仓库初始状态**；用时自建） | 策划 | 否 |
| **`templates/`** | **空模板**，新建时复制 | 维护者 | 是 |
| **`产出/{功能名}/`** | **管线交付物**（01~04 + logs + 看板） | 策划 + AI/程序 | 是 |
| **`案例/`** | **对照样例**（可选，当前无样例） | 维护者 | 是 |
| **`{feature_root}/开发文档/`** | `compile.py` **编译三包** | 工具 | 是（禁止手改） |
| **`skills/workflows/*.json`** | 项目配置（`feature_root` 指向**产出**） | 程序/策划 | 是 |

**铁律**

- `源文档/` **用时自建**，只放原始 docx；仓库初始状态不含此目录。
- **真实功能**的 01~04 必须在 `产出/{功能名}/`；docx 拆解备份在 `产出/…/01-…/源表提取/`。
- `案例/` 只放对照样例；新 docx 跑管线 → 建 `产出/{功能名}/`。

### 1.1 补充与修改看板

每个**产出**功能根目录应有 **`产出/{功能名}/补充与修改看板.md`**：

```text
产出/{功能名}/
├── README.md
├── 补充与修改看板.md          ← ★ 待补充/待修改总表
├── 04-待策划补充/{功能名}/
└── 03-…/待确认事项.md
```

模板见 [templates/04-待策划补充/{功能名}/补充与修改看板.md](templates/04-待策划补充/{功能名}/补充与修改看板.md)（新建功能时复制到产出根目录）。

## 2. 路径变量（Prompt 占位符）

执行 Prompt 前统一替换：

| 占位符 | 含义 | 填写说明 |
|--------|------|----------|
| `{功能名}` | **工作包名称 / 策划案主题** | 系统、玩法、活动、流程改版等；与 `产出/{功能名}` 目录名一致（见 §9） |
| `{feature_root}` | **产出目录** | `产出/{功能名}` |
| `{功能缩写}` | 规则/字段编号缩写 | 如 `R-CHH-001`；**Agent 或程序填**，策划可不填 |
| `{skill_id}` | L1 玩法框架模板 | workflow 选用；**无则留空**，策划可不填 |
| `{项目}` | workflow 文件名（不含 `.json`） | **Agent 或程序填**，如 `myfeature` |

**标准阶段路径**（以下 `{功能名}` 两处必须相同）：

```text
{feature_root}/
├── 00-立项探索/{功能名}/          ← 立项探索 可选
├── 01-原始策划案/{功能名}/
│   ├── 原始策划案.md              ← 原始策划案 定稿（P2+ 主读）
│   └── 源表提取/                  ← docx 内嵌表备份
├── 02-03需求拆解与功能点梳理/         ← ★ 需求拆解/功能点梳理 拆解真源
│   ├── 02-需求拆解.md           ← 策划/运营/产品/老板汇报
│   └── 03-功能点梳理.md         ← 程序/AI 主读；格式见 p3 Skill 与格式真源 docx（若有）
├── 04-待策划补充/{功能名}/
├── 开发文档/                    ← compile 三包（勿手改）
├── logs/                          ← ★ 每次文档更新新建 {YYYYMMDD}-{HHmmss}.log.md
├── 补充与修改看板.md
└── README.md
```

**需求拆解 九步（写入 `{spec_root}/02-需求拆解.md` 单文件）**：

```text
数据源 · 系统内容分解 · 规则 · 边界条件 · 红点 · UI交互 · 状态机 · 校验规则 · 验收标准
```

## 3. 原始策划案放哪里

```text
策划 docx / 口述
      ↓
源文档/{任意文件名}.docx          ← 源文件归档（可选）
      ↓ 原始策划案·Docx转原始案 或 立项探索·玩法大纲与01初稿
产出/{功能名}/01-原始策划案/{功能名}/
      ├── 原始策划案-草稿.md    ← 立项探索·玩法大纲与01初稿 产出，策划审阅
      └── 原始策划案.md         ← 原始策划案 定稿，需求拆解 拆解 @ 此文件
```

| 文件 | 阶段 | 能否进 需求拆解 |
|------|------|-----------|
| `源文档/*.docx` | 输入 | 否（须先转 01） |
| `原始策划案-草稿.md` | 立项探索·玩法大纲与01初稿 | 否（须 原始策划案 定稿） |
| `原始策划案.md` | 原始策划案 定稿 | **是** |

**需求拆解 及以后 @ 引用**：一律指向

```text
产出/{功能名}/01-原始策划案/{功能名}/原始策划案.md
```

不要 @ `源文档/` 下的 docx（除非 原始策划案·Docx转原始案 转换步骤中临时使用）。

## 4. 各阶段：读什么、写什么

### 立项探索 立项探索（可选）

| 步骤 | @ 引用 | 写出路径 |
|------|--------|----------|
| 立项探索·项目发现 | 策划口述 / `源文档/*` | `{feature_root}/00-立项探索/{功能名}/project.json` |
| 立项探索·GameDNA定调 | `…/project.json` | `…/game_dna.json`、`game_dna.md` |
| 立项探索·功能层级与Skill选型 | game_dna + `skills/README.md` | `…/skill选型.md` |
| 立项探索·玩法大纲与01初稿 | 上述 + L1 `design.md` | `…/玩法大纲.md`、`01-…/原始策划案-草稿.md` |

### 原始策划案 原始策划案

| 步骤 | @ 引用 | 写出路径 |
|------|--------|----------|
| 原始策划案·Docx转原始案 | `源文档/*.docx` 或 `原始策划案-草稿.md` | `{feature_root}/01-原始策划案/{功能名}/原始策划案.md` |
| 原始策划案·完整性检查 | `原始策划案.md` | `{feature_root}/01-原始策划案/{功能名}/完整性检查-gap清单.md` |

### 需求拆解 需求拆解（9 步 → 单文档）

**前置 @**：`原始策划案.md` + `skills/workflows/*.json` + L1 Skill（如有）

| 维度 | Prompt | 写入 02 章节 |
|------|--------|--------------|
| 数据源 | 需求拆解·数据源 | §6 数据概要 |
| **系统内容分解** | **需求拆解·系统内容分解** | **§1.5 系统与内容分解** |
| 规则 | 需求拆解·规则 | §3 规则说明 |
| 边界条件 | 需求拆解·边界条件 | §5 边界 |
| 状态机 | 需求拆解·状态机 | §2 状态机 |
| UI交互 | 需求拆解·UI交互 | §4 UI |
| 红点 | 需求拆解·红点 | §6.1 红点 |
| 校验规则 | 需求拆解·校验规则 | 默认跳过；V-xx → 功能点梳理 附录 E.2 |
| 验收标准 | 需求拆解·验收标准 | §7 验收要点 |

**推荐顺序**：需求拆解·数据源 → 需求拆解·系统内容分解 → 需求拆解·规则 → 需求拆解·边界条件 → 需求拆解·状态机 → 需求拆解·UI交互 → 需求拆解·红点 → 需求拆解·校验规则 → 需求拆解·验收标准

**产出路径**：`{feature_root}/02-03需求拆解与功能点梳理/02-需求拆解.md`（单文件）

**写作规范**：[templates/02-需求拆解-写作规范.md](templates/02-需求拆解-写作规范.md)

**汇报主读**：`02-需求拆解.md` — 自然语言；**不含**伪代码、P-xx 大表、数据契约审计。

### 功能点梳理 功能点梳理（程序可读）

| 步骤 | @ 引用 | 写出路径 |
|------|--------|----------|
| 功能点梳理·阅读说明 | 01 + 02 | `03-功能点梳理.md` §0 |
| 功能点梳理·功能点拆分 | 01 + 02 | 各 `## N.` + **怎么实现（伪代码）** |
| 功能点梳理·字段映射 | 02 + 03 | 附录 A + **附录 D/E**（字段、审计、协议、配置表） |
| 功能点梳理·验收场景~5 | 03 | 附录 B/C |

**程序主读**：`03-功能点梳理.md` — 自包含，禁止「见 02」。

### 02 vs 03 内容边界

| 内容 | 02 | 03 |
|------|----|----|
| 规则 | R- 自然语言「规则说明」 | 伪代码 + P-xx 读写 |
| 流程 | 玩家阶段名 | Phase 枚举、状态机 |
| 数据 | §6 数据概要 | 附录 A/D/E |
| **内容族** | **§1.5 SYS-/CNT-** | 按系统/内容类展开功能点 |
| 验收 | T- 用户操作语言 | 附录 B 细场景 |

### 待策划补充～开发管线

| 阶段 | 主读 | 产出 |
|------|------|------|
| 待策划补充 | 01 + 02 + 03 | `{feature_root}/04-待策划补充/{功能名}/` |
| 编译验收 | 02 + 03 + workflow | `{feature_root}/开发文档/程序包.md` 等 + **`logs/{时间}.log.md`** |
| 开发管线 | 03 + `{feature_root}/开发文档/程序包.md` | server/client design 四件套（仓库外）；完成后**追加或新建** logs 条目 |

### 管线执行日志（每次文档更新必写）

**铁律**：只要本次会话改动了 `{feature_root}` 下任意交付文档，结束前**必须**新建一条日志——不限于跑完 编译验收 或全量管线。

| 触发场景 | 示例 |
|----------|------|
| 全量 / 部分管线 | 原始策划案～开发管线 任意组合执行完毕 |
| 单文档局部更新 | 改 `02-需求拆解.md` 某一章、补 R-xx |
| 04 回填回流 | 策划填 04 → Agent 回流 02/03 |
| 编译重跑 | 仅 `compile.py` 后仍须 log（记录 compile 与输入变更） |
| 目录 / 链接 / 规范维护 | 改 README、更新看板 |

写入路径：

```text
{feature_root}/logs/{YYYYMMDD}-{HHmmss}.log.md
```

| 规则 | 说明 |
|------|------|
| 命名 | **结束时刻**本地时间，如 `20260706-151530.log.md` |
| 频次 | 同功能多次更新 → **多条**日志并存，**禁止覆盖**已有 `.log.md` |
| 禁止 | 固定文件名（如 `管线执行报告.md`）、在旧 log 上追加、只口头说明不写文件 |
| 模板 | [templates/logs/模板.log.md](templates/logs/模板.log.md) |
| Prompt | [prompts/编译验收/管线执行日志.md](prompts/编译验收/管线执行日志.md)（名称保留；适用全部文档更新） |

**最小必填**（局部更新可省略未触达阶段）：

1. 元信息：**变更类型**、执行者、feature_root  
2. **本次变更文件清单**（路径列表，须与 git diff 可对齐）  
3. 到达节点 / 是否 compile / 阻塞项  
4. 下次建议起点  

全量管线时仍按模板填 立项探索～开发管线 阶段表；**仅改 02/03 一节**时阶段表未触达项标 `—`，但 §「本次变更」不可省略。

**README 索引**：`{feature_root}/README.md` 的「上次执行记录」链接指向**最新一条** log（按文件名时间排序）。

## 5. 新建功能（操作步骤）

### 5.1 初始化目录

```bash
# 在 GDD SKILL/ 下执行
功能名="你的功能名"
mkdir -p "产出/${功能名}/01-原始策划案/${功能名}"
mkdir -p "产出/${功能名}/02-03需求拆解与功能点梳理"
mkdir -p "产出/${功能名}/04-待策划补充/${功能名}"
mkdir -p "产出/${功能名}/logs"
# 若走 P0：
mkdir -p "产出/${功能名}/00-立项探索/${功能名}"
```

或复制模板：

```bash
cp -r templates/01-原始策划案/{功能名} "产出/${功能名}/01-原始策划案/${功能名}"
# 其余阶段同理
```

### 5.2 归档策划源文件

```text
源文档/你的策划案.docx   → 仅作输入，原始策划案·Docx转原始案 @ 引用
```

### 5.3 创建 workflow

复制 [`skills/workflows/_template.workflow.json`](skills/workflows/_template.workflow.json) → `skills/workflows/{项目}.workflow.json`，将 `{功能名}` 替换为工作包名称。

`feature_root` **必须**与 `产出/` 下文件夹名一致（不含末尾 `{功能名}` 子层）。

### 5.4 选路径

| 情况 | 路径 |

## 6. 详细使用说明

本节说明**在 Cursor 里怎么 @ 文件、发什么消息、产出写到哪里**。  
所有路径相对于 `GDD SKILL/` 子项目根；对话里 @ 时用仓库内的真实路径。

### 6.1 三条上手路径

| 你的情况 | 从哪开始 | 目标 |
|----------|----------|------|
| **A. 有策划 docx** | §6.3 原始策划案 → §6.4 需求拆解 → §6.5 功能点梳理 | 最常见：docx → 01 → 02/03 |
| **B. 01 已定稿** | 直接 §6.4 需求拆解 | 跳过 P1，做需求拆解 |
| **C. 只有想法** | 立项探索·项目发现~4 → 原始策划案 → 需求拆解 | 先立项再规格化 |

**核心原则**

- **@ 的是输入**（01、02、workflow、Prompt 规范）；**写的是输出**（`产出/{功能名}/` 下对应目录）。
- **方式 A（gdd-decompose）**：可说「整包 / 不要停」连续跑多步；**方式 B（半自动）**：一次对话建议只跑 **1 个 Prompt 步骤**（功能点梳理·功能点拆分 可按章节分批）。
- 每步完成后**策划确认**，再进下一步；会话结束必做 **编译验收·管线执行日志 写 logs**。

### 6.2 在 Cursor 里怎么 @

1. 在输入框输入 `@`，搜索文件名或文件夹。
2. **优先 @ 具体 `.md` / `.json`**，不要只 @ 整个 `案例/`（上下文过大易漏细节）。
3. 同时 @ **本步 Prompt 文件**（如 `prompts/需求拆解/规则.md`），让 Agent 按正文铁律执行。
4. 消息正文 = **替换占位符后的提示词正文** + 一句任务说明（见下文示例）。

**@ 引用写法示例**（Cursor 会自动补全路径）：

```text
@GDD SKILL/产出/{功能名}/01-原始策划案/{功能名}/原始策划案.md
@GDD SKILL/skills/workflows/{项目}.workflow.json
@prompts/需求拆解/规则.md
```

### 6.3 阶段一：01 定稿（P1）

**何时做**：有 docx / 草稿，还没有 `原始策划案.md`，或 docx 有更新。

**@ 引用**

| 文件 | 路径 |
|------|------|
| 策划源（原始策划案·Docx转原始案） | `源文档/{策划案}.docx` 或 `…/原始策划案-草稿.md` |
| Prompt | `prompts/原始策划案/Docx转原始案.md` |

**对话示例（原始策划案·Docx转原始案）**

```text
@源文档/{你的策划案}.docx
@prompts/原始策划案/Docx转原始案.md

请按 原始策划案·Docx转原始案 提示词正文执行：
- 功能名：{功能名}
- feature_root：产出/{功能名}
- 产出：产出/{功能名}/01-原始策划案/{功能名}/原始策划案.md
- 保留 docx 全部表格与章节，标注继承现网/新增/改动
请直接写入文件，不要只输出大纲。
```

**原始策划案·完整性检查 完整性检查** — @ `原始策划案.md` + `prompts/原始策划案/完整性检查.md`  
产出：`01-…/完整性检查-gap清单.md`（只列 gap，不扩写 01）。

**门禁**：gap 清单无 立项探索 级阻塞 → 策划确认 01 → 进入 P2。

### 6.4 阶段二：需求拆解（需求拆解 · 02）

**何时做**：`原始策划案.md` 已定稿，需要生成 **02-需求拆解**（9 步、R-/SYS-/CNT-/P-/V- 编号）。

**固定顺序**（不可乱序）：

```text
需求拆解·数据源 → 需求拆解·系统内容分解 → 需求拆解·规则 → 需求拆解·边界条件 → 需求拆解·状态机 → 需求拆解·UI交互 → 需求拆解·红点 → 需求拆解·校验规则 → 需求拆解·验收标准
```

#### 6.4.1 各步 @ 引用速查

| 步骤 | 必 @ | 可选 @（有 L1 时） | 产出 |
|------|------|-------------------|------|
| **需求拆解·数据源** | `01/…/原始策划案.md`、`skills/workflows/{项目}.workflow.json` | L1 meta/tech | `02-需求拆解.md` §6 |
| **需求拆解·系统内容分解** | 01 + 02 §6 | — | 02 §1.5 |
| **需求拆解·规则** | 01 + 02 §1.5 + workflow | L1 design.md | 02 §3 |
| **需求拆解·边界条件** | 01 + 02 §3 | L1 design.md | 02 §5 |
| **需求拆解·状态机** | 01 + 02 §3 | L1 design/ux | 02 §2 |
| **需求拆解·UI交互** | 01 + 02 §3 | L0 ux、tech | 02 §4 |
| **需求拆解·红点** | 01 + 02 §4 | — | 02 §6.1 |
| **需求拆解·校验规则** | 01 + 02 + 03（若已有） | — | 03 附录 E.2 |
| **需求拆解·验收标准** | 01 + 02 已完成章节 | L1 qa.md | 02 §7 |

> **无 L1**：`skill_id` 留空；02 从 01 全量写。  
> **有 L1**：只写 delta，通用规则写「继承 {skill_id} R-xxx」。  
> **P-xx / 伪代码 / 审计**：功能点梳理 → `03-功能点梳理.md` 附录 A~E。

#### 6.4.2 对话示例：需求拆解·数据源（必须先做）

```text
@产出/{功能名}/01-原始策划案/{功能名}/原始策划案.md
@skills/workflows/{项目}.workflow.json
@prompts/需求拆解/数据源.md
@templates/02-需求拆解-写作规范.md

请按 需求拆解·数据源 执行：
- 功能名：{功能名}
- feature_root：产出/{功能名}
- 产出：02-需求拆解.md §6 数据概要（表名列表，不含 P-xx 大表）
请直接写入文件。
```

#### 6.4.3 对话示例：需求拆解·规则

```text
@产出/{功能名}/01-原始策划案/{功能名}/原始策划案.md
@产出/{功能名}/02-03需求拆解与功能点梳理/02-需求拆解.md
@prompts/需求拆解/规则.md

请对「{功能名}」执行 需求拆解·规则：
- 产出：02-需求拆解.md §3
- 每条 R- 为自然语言「规则说明」，不含伪代码
- 标注来源 01 §x.x
请直接写入文件。
```

#### 6.4.4 其余 需求拆解 维度

复制对应 `prompts/需求拆解/P2-*.md` 的「提示词正文」，替换占位符，@ 上表「必 @」列文件，**改本步任务与输出路径**即可。  
需求拆解·边界条件 ~ 需求拆解·验收标准 的写法与 需求拆解·规则 相同，只是 Prompt 文件和产出子目录不同。

**需求拆解 完成门禁**

- [ ] **`02-需求拆解.md` 已产出**（汇报可读；含规则/UI/边界/数据概要）
- [ ] 九步内容已写入 `02-需求拆解.md`（单文件）
- [ ] 核心 R-xx 含伪代码 + P-xx / 表列依赖
- [ ] **`02-…/数据源/数据契约审计.md` 已产出**（或等价章节在 02 单文档 §6 内）
- [ ] 核心 R-xx **无变量无落点**；阻塞项已登记 Q-D 并链到看板

**功能点梳理 完成门禁**

- [ ] **`03-功能点梳理.md` 已产出**（程序主读；格式见 p3 Skill / 格式真源 docx）
- [ ] §0 阅读说明 + 各功能点章 + 附录 A/B/C

**开发管线 模块门禁**（某模块开工前）：该模块在数据契约审计中 **无契约层阻塞**。

## 8. 常见错误

| 错误 | 正确做法 |
|------|----------|
| 把 01 写在 `源文档/` | 01 定稿必须在 `产出/…/01-原始策划案/{功能名}/` |
| 02 写到 `templates/` | 只复制模板一次，产出写 `产出/` |
| 仍创建 `02-…/规则/` 多文件夹 | 写入 `02-需求拆解.md` 对应 § 章节 |
| 需求拆解 在 02 写伪代码 / P-xx | 02 仅自然语言；功能点梳理 → 03 附录 |
| 需求拆解 @ docx 不转 01 | 先 原始策划案·Docx转原始案 生成 `原始策划案.md` |
| 手改 `{feature_root}/开发文档/` | 改 02/03 后重新 `compile.py` |
| `feature_root` 与目录名不一致 | workflow 与 `产出/` 文件夹名对齐 |
| AI 跑管线时改 `skills/` | Skill 变更须维护者确认；业务只写 `产出/` |
| 新功能写到 `案例/` | 真实交付写 `产出/`；`案例/` 仅对照样例 |
| 未写 logs/ 执行日志 | **每次更新** 01/02/03/04/看板/README 等交付文档后须 编译验收·管线执行日志 **新建** log；禁止覆盖 |
| 一次对话跑完 需求拆解 九步 | 建议每步一个 Prompt，便于策划中途确认 |
| @ 整个产出文件夹 | 优先 @ 具体 md/json，避免上下文过大 |
| 功能点梳理·功能点拆分 在 需求拆解 核心 R- 未完成时执行 | 须先完成 需求拆解·规则 规则说明，否则 03 缺业务输入 |
