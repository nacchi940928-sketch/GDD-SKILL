# 02-需求拆解 — 写作规范

> **读者**：策划、运营、产品、管理层。  
> **不是**：程序实现规格（那是 `03-功能点梳理.md`）。

---

## 02 vs 03

| | 02 需求拆解.md | 03 功能点梳理.md |
|--|----------------|------------------|
| 语言 | **自然语言**，像策划案扩写 | 技术规格，可交给程序/AI |
| 规则 | 何时、对谁、发生什么、为什么 | R-xx **伪代码**、检测位置、P-xx 读写 |
| 流程 | 玩家/界面视角的阶段描述 | Phase 枚举、状态机、协议时序 |
| 数据 | 需要哪些表/配置（**表名 + 代表字段**） | 附录 A 全字段、配置表、协议、审计 |
| 编号 | R-/EX-/T- 作**对照锚点**；配置项写 **P-xx + `表.字段`** | P-xx 全文、附录 A |
| 禁止 | 伪代码、协议表、Const 审计、数据契约 | 「见 02」「见策划案」 |

## 规则条目格式（02）

```markdown
## R-{缩写}-001 {规则标题}

**边界**：继承现网 · {模块名}（仅写 delta 时说明改动点）
<!-- 或：本次新增 / 本次改动（一句话说明相对现网差异） -->

**规则说明**：（2~5 句自然语言：触发情境 → 系统行为 → 玩家可见结果 → 例外）

【待确认】…（如有）

**来源**：01 §x.x
```

**边界**取值：`继承现网` · `本次新增` · `本次改动`（与 01 边界标注一致，落到每条规则）。

**不要写**：`检测位置`、`检测方式`、代码块、`| 读/写 | P-xx |` 表。

竞争、排序、计时类规则须在「规则说明」中写清 **终裁方**（由谁判定结果）；01 有歧义时须择一，不得同时保留「轮流」与「同时」。

## §1.x 范围：做 / 不做（必写）

在 **§1 功能概述** 中增加范围表：

```markdown
### 1.x 范围：做 / 不做

| 做（本包范围） | 不做（MVP 或非目标） |
|----------------|----------------------|
| 从 01 提取     | 从 01 提取；无则【待确认】 |
```

无明确「不做」时仍须建表，第二列填【待确认】，禁止留空。

## 2. 流程与状态

> **§2 瘦身铁律**：本章只写**阶段名称**、**一行阶段内状态**（玩家能做什么/不能做什么）、**标注来源**、**「详见 R-xxx」**。**禁止**在本章写具体秒数、人数上下限、终裁方——一律放在 §3。

### 推断与来源标注（§2 必用）

| 标记 | 含义 | 何时使用 |
|------|------|----------|
| **【01 原文】** | 策划案明确写出 | 01 有对应句 |
| **【决策稿】** | P4.5 外部决策稿闭合 | 业务逻辑表已确认 |
| **【推断·待确认】** | Agent/工程推测，01 未写 | UI 交互形态、能否跳过等 |

### 2.1 单局流程

选角 → 匹配中 → 对局内（每轮：抢道具 → 放道具 → 跑酷 → 小结算）→ 总结算 →（可选）加赛
```

**示例（阶段内状态 · 瘦身写法）**：

```markdown
#### 2.2.1 选角阶段

**阶段内状态**：展示全部鸟卡、未解锁灰置【01 原文】；【推断·待确认：选中后发起匹配】；整局锁定【决策稿】。详见 R-CHH-002。
```

**不要写**：`LOBBY`、`P-17`、`MatchStartReq`（放 03）；**不要在 §2 写** `600s`、`2~4 人` 等参数（放 §3 R-）。

### §2.x 阶段内状态（每条子流程必写）

每个阶段除名称外，须一行说明：

- 该阶段内玩家能否移动、是否忽略重力等特殊物理
- 倒计时是否**必须等满**（全员提前完成是否仍等待）
- 能否放弃/跳过/主动丢弃操作
- 失败/超时如何处置 → 引用 R-{缩写}-xxx

示例：

```markdown
- **放置阶段**：四人在网格内自由移动（忽略重力）；须等满倒计时才进入跑酷；无主动丢弃 → 见 R-XXX-009
```

不得在同一 §2 中既写「轮流」又写「同时」；若 01 有歧义，按 §3 已定 R- 统一表述。

## 系统与内容分解（02 · §1.5）

在 **§1 功能概述** 之后、**§2 流程** 之前，按 **§2.1 主流程顺序** 列出各阶段的内容子类（策划语义索引，不是规则正文）。

> **铁律**：§1.5 **节序 = §2 玩家流程**，不是按后端模块/技术域排序。每节标题标注 `· §2.x.x` 锚点。

```markdown
## 1.5 系统与内容分解

> 节序 = §2.1 主流程

### SYS-CHH-001 入口与选角 · §2.2.1
...
### SYS-CHH-002 匹配与进房 · §2.2.2
...
```

**编号**：`SYS-{缩写}-{序号}` 按**流程阶段**递增；`CNT-{缩写}-{序号}` 内容子类编号稳定，不因 SYS 重排而改号。

**§1.5 写什么**：子类名称、策划定义、数量级、对应 §6 表名、预留 R-/UI、边界。

**§1.5 不要写**：伪代码、P-xx 列、逐行配置、完整实体清单（代表例 1~3 个即可）。

**可跳过**：纯流程/入口改版且无新内容子类 → 一节说明「本包无新增 CNT」，指向 §3/§6。

§3 规则可写：`适用于 CNT-CHH-001`。
