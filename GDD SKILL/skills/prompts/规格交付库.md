# 规格交付 Prompt 库（Part 2）

> **工作重点**：无论哪位策划、何种风格的 01 原始策划案，经本库执行后，产出**统一规范、程序与 AI 可执行**的 02 + 03。  
> Part 1（策划辅助）见 [立项探索/README.md](立项探索/README.md)。

## 1. 两部分 Prompt 分工

| 部分 | 目录 | 输入 | 输出 | 角色 |
|------|------|------|------|------|
| **Part 1 策划辅助** | `立项探索/` | 模糊想法、口述、竞品 | 00 立项探索、01 草稿 | 帮策划**写**案 |
| **Part 2 规格交付** | `原始策划案/`～`开发管线/` | **策划定稿 01** | 02/03/04 + 编译 + 开发管线 | 帮程序/AI**读**案 |

```text
Part 1 策划辅助（可选）          Part 2（核心）
立项探索 → 01 草稿    →    原始策划案定稿 → 需求拆解 → 功能点梳理 → 待策划补充 → 编译验收 → 开发管线
                         ↑
              策划 docx 也可直接从「原始策划案」进入，跳过立项探索
```

**Part 2 交付物**：`02-需求拆解` + `03-功能点梳理`（及填完的 `04`）→ `{feature_root}/开发文档/程序包.md`

**Prompt 与 Skill 边界**

| | Prompt（本库） | Skill（`skills/`） |
|--|----------------|-------------------|
| 内容 | 文档格式、路径、编号、铁律 | 抽象框架与横切规范 |
| 业务 | **禁止**写具体功能名词 | **禁止**写 L2 案例正文 |
| 变更 | 维护者迭代 | **须维护者确认**；AI 跑管线时不得改 Skill |

## 2. 统一输入契约（所有 Part 2 Prompt 共用）

### 2.1 占位符

| 占位符 | 含义 | 填写说明 |
|--------|------|----------|
| `{功能名}` | **工作包名称 / 策划案主题** | 系统、玩法、活动、流程改版、界面优化等**整包**主题；与 `产出/{功能名}` 目录名一致 |
| `{feature_root}` | 产出根路径 | `产出/{功能名}`（程序用，策划记「产出目录」即可） |
| `{功能缩写}` | 编号前缀 | 大写英文缩写，如 `R-{缩写}-001`；**Agent 或程序填**，策划可不填 |
| `{skill_id}` | L1 玩法框架 id | 来自 workflow；**无则留空**，策划可不填 |
| `{项目}` | workflow 文件名（不含 .json） | 如 `skills/workflows/{项目}.workflow.json`；**Agent 或程序填** |

> `{功能名}` 不是 03 里某一个功能点，而是**这一次走完整管线的策划案工作包**。Prompt 正文只写文档规范与占位符，不写具体业务。

### 2.2 必读输入（按阶段递增）

| 阶段 | 必须 @ |
|------|--------|
| **原始策划案** | `源文档/*.docx` 或已有 01 草稿 |
| **需求拆解·数据源**（首个） | `{feature_root}/01-…/原始策划案.md` + `skills/workflows/{项目}.workflow.json` + L1 `meta/design/tech.md` |
| **需求拆解 其余** | 01 + `02-需求拆解.md`（按维度依赖递增） |
| **功能点梳理** | 01 + `02-需求拆解.md` + L1 skill |
| **待策划补充** | 01 + `02-需求拆解.md` + `03-功能点梳理.md` |
| **决策稿对账（P4.5）** | 用户 @ 外部决策稿 + `{feature_root}/01~04` + 看板 |
| **编译验收/开发管线** | 02 + 03 + `{feature_root}/开发文档/程序包.md` + workflow |

**01 定稿路径（唯一）**：

```text
{feature_root}/01-原始策划案/{功能名}/原始策划案.md
```

### 2.3 Part 2 公共铁律

1. **不改意图**：规格化表达，不擅自改策划业务决策
2. **不遗漏**：01 每个章节、表格、规则须在 02 或 03 有对应条目
3. **不跳转**：禁止「见原始文档」「见 02/xx」——03 必须自包含
4. **先概要后规格**：需求拆解 写策划语言；P-xx / 伪代码 / 审计在 **功能点梳理 → 03 附录**
5. **编号唯一**：R / EX / PRE / LIM / RD / V / T / B / E / P 全局唯一
6. **标注来源**：每条标注 `来源：01 §x.x`
7. **L1 继承**：框架已有写 `继承 {skill_id} R-xxx`，只写 delta
8. **可实现**：02 写清业务；**03** 写检测位置、数据依赖、伪代码（见 [02-需求拆解-写作规范](../templates/02-需求拆解-写作规范.md)）
9. **路径固定**：产出只在 `{feature_root}/` 下，见 [使用指导.md](../使用指导.md)
10. **歧义消歧**：01 出现时序矛盾词（轮流/同时/并行/依次）→ 02 须择一写清
11. **终裁归属**：竞争、排序、计时类 R- 须写「由谁终裁」；无依据则【待确认】
12. **02/03 一致**：03 伪代码不得与 02 已定 R- 冲突；P4.5 对账后须同步 03
13. **禁止读程序反馈/**：首次 P1～P4 不得 @ `程序反馈/`；对账走 P4.5 显式触发

## 4. Part 2 全流程（推荐顺序）

```text
原始策划案·Docx转原始案  docx/草稿 → 01 定稿
原始策划案·完整性检查  01 完整性 gap 清单（不扩写）
  ↓
需求拆解·数据源 → 需求拆解·系统内容分解 → 需求拆解·规则 → 需求拆解·边界条件 → 需求拆解·状态机 → 需求拆解·UI交互 → 需求拆解·红点 → 需求拆解·校验规则 → 需求拆解·验收标准
  ↓
功能点梳理·阅读说明 → 功能点梳理·功能点拆分（可分批）→ 功能点梳理·字段映射 → 功能点梳理·验收场景 → 功能点梳理·待确认事项 → 功能点梳理·Feature对齐
  ↓
待策划补充·生成待补充清单 → 策划回填 04 → 待策划补充·策划回填验收 验收 ──┐
  ↑                              │ 未通过
  └──────────────────────────────┘
  ↓
（可选 · 用户显式 @ 决策稿）决策稿对账·外部决策稿对账 → 回流 01~04 + logs
  ↓
编译验收·职能分轨检查 分轨检查 → 编译验收·执行编译验收 compile → 编译验收·策划验收清单 策划验收 → 编译验收·管线执行日志 执行日志
  ↓
开发管线·后端管线编排 后端管线 → 开发管线·前端管线编排 前端管线 → 开发管线·增量开发继承现网 增量核对（可选）→ 更新 logs（新建条目）

（以下不在 Part 2 自动流程内 — 须维护者另开会话显式触发）

规范反哺·生成规范反哺报告 → 产出/{功能名}/规范反哺报告.md → 人工审阅 → 另会话改 prompts/skills（S1～S7）
```

### 阶段门禁（进入下一步前须满足）

| 门禁 | 条件 |

| 编译验收 → 开发管线 | compile 成功；`{feature_root}/开发文档/` 三包生成；**编译验收·管线执行日志 已写 logs/**（**每次文档更新**均须新建，非仅 编译验收 全量） |

## 6. 统一 Prompt 结构（每个 Part 2 文件必含）

每个 `prompts/原始策划案～开发管线/*.md` 的「提示词正文」按以下顺序组织：

```text
【规格交付 · Part 2】          ← 身份与目标（1 段）
功能名 / feature_root / 缩写 / skill_id   ← 占位符块
【@ 必读输入】                  ← 本步须 @ 的文件列表
【输出路径】                    ← 完整 {feature_root}/… 路径
【本步任务】                    ← 具体做什么
【本步格式要求】                ← 编号、表格、标准块
【Part 2 公共铁律】              ← 引用第 2.3 节（可精简复述）
【本步铁律】                    ← 本维度特有禁止项
【完成后自检】                  ← 勾选清单
请直接写入文件，不要只输出大纲。
```

每个 Prompt 文件在「提示词正文」代码块**之后**另附 **## 输入内容示例**（占位符表 + @ 引用 + 可选补充说明），**勿与正文一并复制**。

公共头模板见 [公共/规格交付-公共头.md](公共/规格交付-公共头.md)。

## 7. 02 vs 03 分工（避免重复与遗漏）

| 维度 | 02 需求拆解.md | 03 功能点梳理.md |
|------|----------------|------------------|
| 读者 | **策划、运营、产品、老板** | **程序、AI 开发管线** |
| 语言 | 自然语言 | 伪代码 + P-xx + 协议 |
| 组织 | 九步单文档（含 §1.5） | 功能点 + 附录 A~E |
| 规则 | R-「规则说明」段落 | 「怎么实现」+ 读写表 |
| 数据 | §6 表名概要 | 附录 A/D/E |
| 引用 | 可指向 03 | **禁止**「见 02」 |

**原则**：02 **可读可评审**；03 **可独立开发**。同一规则：02 写「做什么」，03 写「怎么做」。

## 8. 不同策划案的统一化策略

| 策划案差异 | Part 2 如何处理 |
|------------|-----------------|
| 章节顺序不同 | 原始策划案·Docx转原始案 归并为标准六章；功能点梳理 按功能模块重排 |
| 表格 vs 叙述混用 | 需求拆解 提取为编号条目；功能点梳理 保留原表格 |
| 缺 UI / 缺配置 | 原始策划案·完整性检查 报 gap；待策划补充 生成待补充 |
| 数值未定 | 02/03 标【待确认】+ 建议值；待策划补充 汇总给策划 |
| 继承现网描述模糊 | 需求拆解·规则 **边界** 备注写对接点；03 写 delta；04 列 Q-xx |
| 已有 L1 框架 | workflow 选 skill；需求拆解 只写 delta |
