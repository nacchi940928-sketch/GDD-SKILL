## 1. 目录分工（不要混用）

| 目录 | 角色 | 谁写 | 是否进 Git |
|------|------|------|------------|
| **`源文档/`** | **仅原始 doc**（docx、ppt）；不含提取表 | 策划 | 可选 |
| **`templates/`** | **空模板**，新建时复制 | 维护者 | 是 |
| **`产出/{功能名}/`** | **管线交付物**（01~04 + logs + 看板） | 策划 + AI/程序 | 是 |
| **`案例/`** | **对照样例**（仅学习参考，如竞技场高级赛） | 维护者 | 是 |
| **`outputs/{功能名}/`** | `compile.py` **编译三包** | 工具 | 是（禁止手改） |
| **`workflows/*.json`** | 项目配置（`feature_root` 指向**产出**） | 程序/策划 | 是 |

**铁律**

- `源文档/` **只放原始 doc**，不放内嵌表、提取稿、配置表。
- **真实功能**的 01~04 必须在 `产出/{功能名}/`；docx 拆解备份在 `产出/…/01-…/源表提取/`。
- `案例/` 只放对照样例；新 docx 跑管线 → 建 `产出/{功能名}/`。

### 1.1 补充与修改看板

每个**产出**功能根目录应有 **`产出/{功能名}/补充与修改看板.md`**：

```text
产出/{功能名}/
├── README.md
├── 补充与修改看板.md          ← ★ 待补充/待修改总表
├── 04-待策划补充/{功能名}/
└── 03-…/待确认事项.md
```

示例：[产出/超级鸡马/补充与修改看板.md](产出/超级鸡马/补充与修改看板.md)  
对照样例（非产出）：[案例/竞技场高级赛/](案例/竞技场高级赛/)

## 2. 路径变量（Prompt 占位符）

执行 Prompt 前统一替换：

| 占位符 | 含义 | 填写说明 |
|--------|------|----------|
| `{功能名}` | 功能中文名，与**产出**子目录名一致 | 见 §9 |
| `{feature_root}` | **产出**根路径 | `产出/{功能名}` |
| `{功能缩写}` | 编号用英文缩写 | 如 `R-{缩写}-001` |
| `{skill_id}` | L1 框架 Skill id | workflow `selected_skills`；无 L1 则留空 |
| `{项目}` | workflow 文件名（不含 `.json`） | 如 `workflows/arena.workflow.json` → `arena` |

**标准阶段路径**（以下 `{功能名}` 两处必须相同）：

```text
{feature_root}/
├── 00-立项探索/{功能名}/          ← P0 可选
├── 01-原始策划案/{功能名}/
│   ├── 原始策划案.md              ← P1 定稿（P2+ 主读）
│   └── 原始策划案-草稿.md          ← P0-4 草稿
├── 02-需求拆解/{功能名}/
│   ├── 规则/
│   ├── 边界条件/
│   ├── 红点/
│   ├── 数据源/
│   ├── UI交互/
│   ├── 状态机/
│   ├── 校验规则/
│   └── 验收标准/
├── 03-功能点梳理/{功能名}/
│   ├── 0-阅读说明.md
│   ├── 字段映射.md
│   ├── 验收场景.md
│   ├── 待确认事项.md
│   └── 功能点/*.md
└── 04-待策划补充/{功能名}/
    ├── README.md
    └── 01~08-*.md
├── logs/
│   └── {YYYYMMDD}-{HHmmss}.log.md
├── 补充与修改看板.md              ← 待补充/待修改总表（P4 维护）
└── README.md                      ← 案例入口
```

> 外层 `产出/超级鸡马` 是功能包；内层 `…/01-原始策划案/超级鸡马/` 与 `compile.py`、`workflow.feature_root` 约定一致。

## 3. 原始策划案放哪里

```text
策划 docx / 口述
      ↓
源文档/{任意文件名}.docx          ← 源文件归档（可选）
      ↓ P1-1 或 P0-4
产出/{功能名}/01-原始策划案/{功能名}/
      ├── 原始策划案-草稿.md    ← P0-4 产出，策划审阅
      └── 原始策划案.md         ← P1 定稿，P2 拆解 @ 此文件
```

| 文件 | 阶段 | 能否进 P2 |
|------|------|-----------|
| `源文档/*.docx` | 输入 | 否（须先转 01） |
| `原始策划案-草稿.md` | P0-4 | 否（须 P1 定稿） |
| `原始策划案.md` | P1 定稿 | **是** |

**P2 及以后 @ 引用**：一律指向

```text
产出/{功能名}/01-原始策划案/{功能名}/原始策划案.md
```

不要 @ `源文档/` 下的 docx（除非 P1-1 转换步骤中临时使用）。

## 4. 各阶段：读什么、写什么

### P0 立项探索（可选）

| 步骤 | @ 引用 | 写出路径 |
|------|--------|----------|
| P0-1 | 策划口述 / `源文档/*` | `{feature_root}/00-立项探索/{功能名}/project.json` |
| P0-2 | `…/project.json` | `…/game_dna.json`、`game_dna.md` |
| P0-3 | game_dna + `skills/README.md` | `…/skill选型.md` |
| P0-4 | 上述 + L1 `design.md` | `…/玩法大纲.md`、`01-…/原始策划案-草稿.md` |

### P1 原始策划案

| 步骤 | @ 引用 | 写出路径 |
|------|--------|----------|
| P1-1 | `源文档/*.docx` 或 `原始策划案-草稿.md` | `{feature_root}/01-原始策划案/{功能名}/原始策划案.md` |
| P1-2 | `原始策划案.md` | `{feature_root}/01-原始策划案/{功能名}/完整性检查-gap清单.md` |

### P2 需求拆解（8 维度）

**前置 @**：`原始策划案.md` + `workflows/*.json` + L1 Skill（如有）

| 维度 | Prompt | 输出目录 |
|------|--------|----------|
| 数据源 | P2-DS | `{feature_root}/02-需求拆解/{功能名}/数据源/` |
| 规则 | P2-R | `…/规则/` |
| 边界条件 | P2-EX | `…/边界条件/` |
| 状态机 | P2-SM | `…/状态机/` |
| UI交互 | P2-UI | `…/UI交互/` |
| 红点 | P2-RD | `…/红点/` |
| 校验规则 | P2-V | `…/校验规则/` |
| 验收标准 | P2-T | `…/验收标准/` |

**推荐顺序**：P2-DS → P2-R → P2-EX → P2-SM → P2-UI → P2-RD → P2-V → P2-T

### P3 功能点梳理

| 步骤 | @ 引用 | 写出路径 |
|------|--------|----------|
| P3-1 | 01 + 02 全目录 | `{feature_root}/03-功能点梳理/{功能名}/0-阅读说明.md` |
| P3-2 | 同上 | `…/功能点/*.md` |
| P3-3~6 | 03 已有文件 | `字段映射.md`、`验收场景.md` 等 |

**程序主读入口**：

```text
产出/{功能名}/03-功能点梳理/{功能名}/0-阅读说明.md
```

### P4~P6

| 阶段 | 主读 | 产出 |
|------|------|------|
| P4 | 01 + 02 + 03 | `{feature_root}/04-待策划补充/{功能名}/` |
| P5 | 02 + 03 + workflow | `outputs/{功能名}/程序包.md` 等 + **`logs/{时间}.log.md`** |
| P6 | 03 + `outputs/程序包.md` | server/client design 四件套（仓库外）；完成后**追加或新建** logs 条目 |

### 管线执行日志（每次必写）

每次策划案走完（或**一次 Agent 会话结束**）工作流，须用 **P5-4** 写入：

```text
{feature_root}/logs/{YYYYMMDD}-{HHmmss}.log.md
```

| 规则 | 说明 |
|------|------|
| 命名 | 结束时刻本地时间，如 `20260706-151530.log.md` |
| 频次 | 同功能多次执行 → **多条**日志，禁止覆盖 |
| 模板 | [templates/logs/模板.log.md](templates/logs/模板.log.md) |
| Prompt | [prompts/P5/P5-4-管线执行日志.md](prompts/P5/P5-4-管线执行日志.md) |
| 时机 | P5-3 之后必做；仅跑到 P2/P3 中断时也须写（记录到达节点） |

## 5. 新建功能（操作步骤）

### 5.1 初始化目录

```bash
# 在 GDD SKILL/ 下执行
功能名="你的功能名"
mkdir -p "产出/${功能名}/01-原始策划案/${功能名}"
mkdir -p "产出/${功能名}/02-需求拆解/${功能名}"
mkdir -p "产出/${功能名}/03-功能点梳理/${功能名}/功能点"
mkdir -p "产出/${功能名}/04-待策划补充/${功能名}"
mkdir -p "产出/${功能名}/logs"
# 若走 P0：
mkdir -p "产出/${功能名}/00-立项探索/${功能名}"
```

或复制模板：

```bash
cp -r templates/01-原始策划案/{功能名} "产出/${功能名}/01-原始策划案/${功能名}"
# 其余阶段同理
```

### 5.2 归档策划源文件

```text
源文档/你的策划案.docx   → 仅作输入，P1-1 @ 引用
```

### 5.3 创建 workflow

复制 `workflows/arena.workflow.json` → `workflows/{项目}.workflow.json`：

```json
{
  "feature_root": "产出/{功能名}",
  "selected_skills": ["resolution_standard", "interaction_feedback"],
  "skill_configs": { }
}
```

`feature_root` **必须**与 `产出/` 下文件夹名一致（不含末尾 `{功能名}` 子层）。

### 5.4 选路径

| 情况 | 路径 |
|------|------|
| 有 docx / 完整 01 | 跳过 P0 → P1-1 → P2 |
| 只有想法 | P0-1~4 → P1 定稿 → P2 |

### 5.5 编译

```bash
cd "GDD SKILL"
python tools/compile.py 产出/{功能名} --workflow workflows/{项目}.workflow.json
```

产出：`outputs/{功能名}/程序包.md | 测试包.md | 策划包.md`

## 6. 详细使用说明

本节说明**在 Cursor 里怎么 @ 文件、发什么消息、产出写到哪里**。  
所有路径相对于 `GDD SKILL/` 子项目根；对话里 @ 时用仓库内的真实路径。

### 6.1 三条上手路径

| 你的情况 | 从哪开始 | 目标 |
|----------|----------|------|
| **A. 有策划 docx** | §6.3 P1 → §6.4 P2 → §6.5 P3 | 最常见：docx → 01 → 02/03 |
| **B. 01 已定稿** | 直接 §6.4 P2 | 跳过 P1，做需求拆解 |
| **C. 只有想法** | P0-1~4 → P1 → P2 | 先立项再规格化 |

**核心原则**

- **@ 的是输入**（01、02、workflow、Prompt 规范）；**写的是输出**（`产出/{功能名}/` 下对应目录）。
- 一次对话建议只跑 **1 个 Prompt 步骤**（P3-2 可按章节分批）。
- 每步完成后**策划确认**，再进下一步；会话结束必做 **P5-4 写 logs**。

### 6.2 在 Cursor 里怎么 @

1. 在输入框输入 `@`，搜索文件名或文件夹。
2. **优先 @ 具体 `.md` / `.json`**，不要只 @ 整个 `案例/`（上下文过大易漏细节）。
3. 同时 @ **本步 Prompt 文件**（如 `prompts/P2/P2-R-规则.md`），让 Agent 按正文铁律执行。
4. 消息正文 = **替换占位符后的提示词正文** + 一句任务说明（见下文示例）。

**@ 引用写法示例**（Cursor 会自动补全路径）：

```text
@GDD SKILL/案例/竞技场高级赛/01-原始策划案/竞技场高级赛/原始策划案.md
@GDD SKILL/workflows/arena.workflow.json
@GDD SKILL/prompts/P2/P2-R-规则.md
```

### 6.3 阶段一：01 定稿（P1）

**何时做**：有 docx / 草稿，还没有 `原始策划案.md`，或 docx 有更新。

**@ 引用**

| 文件 | 路径 |
|------|------|
| 策划源（P1-1） | `源文档/{策划案}.docx` 或 `…/原始策划案-草稿.md` |
| Prompt | `prompts/P1/P1-1-Docx转原始案.md` |

**对话示例（P1-1）**

```text
@源文档/竞技场高级赛（纷乱的群殴锦标赛）活动优化.docx
@prompts/P1/P1-1-Docx转原始案.md

请按 P1-1 提示词正文执行：
- 功能名：竞技场高级赛
- feature_root：案例/竞技场高级赛
- 产出：案例/竞技场高级赛/01-原始策划案/竞技场高级赛/原始策划案.md
- 保留 docx 全部表格与章节，标注继承现网/新增/改动
请直接写入文件，不要只输出大纲。
```

**P1-2 完整性检查** — @ `原始策划案.md` + `prompts/P1/P1-2-完整性检查.md`  
产出：`01-…/完整性检查-gap清单.md`（只列 gap，不扩写 01）。

**门禁**：gap 清单无 P0 级阻塞 → 策划确认 01 → 进入 P2。

### 6.4 阶段二：需求拆解（P2 · 02）

**何时做**：`原始策划案.md` 已定稿，需要生成 **02-需求拆解**（8 维度、R-/P-/V- 编号）。

**固定顺序**（不可乱序）：

```text
P2-DS → P2-R → P2-EX → P2-SM → P2-UI → P2-RD → P2-V → P2-T
```

#### 6.4.1 各步 @ 引用速查

| 步骤 | 必 @ | 可选 @（有 L1 时） | 产出目录 |
|------|------|-------------------|----------|
| **P2-DS** | `01/…/原始策划案.md`、`workflows/{项目}.workflow.json` | `skills/design/{skill_id}/meta.md`、`tech.md` | `02-…/数据源/` |
| **P2-R** | 01 + `02-…/数据源/字段映射索引.md` + workflow | `skills/design/{skill_id}/design.md` | `02-…/规则/` |
| **P2-EX** | 01 + 字段映射索引 + `02-…/规则/` | L1 design.md | `02-…/边界条件/` |
| **P2-SM** | 01 + 字段映射 + 规则/ | L1 design.md、ux.md | `02-…/状态机/` |
| **P2-UI** | 01 + 规则/ + 数据源/ | L0 ux、tech | `02-…/UI交互/` |
| **P2-RD** | 01 + UI交互/ + 规则/ | — | `02-…/红点/` |
| **P2-V** | 01 + 字段映射 + 规则/ | — | `02-…/校验规则/` |
| **P2-T** | 01 + 02 已完成的各维度 | L1 qa.md | `02-…/验收标准/` |

> **无 L1 框架**：`skill_id` 留空，不 @ `skills/design/`；02 全部从 01 全量写。  
> **有 L1**：workflow 里 `selected_skills` 含框架 id 时，P2 只写 **delta**，通用规则写「继承 {skill_id} R-xxx」。

#### 6.4.2 对话示例：P2-DS（必须先做）

```text
@案例/竞技场高级赛/01-原始策划案/竞技场高级赛/原始策划案.md
@workflows/arena.workflow.json
@skills/design/tournament_bracket/meta.md
@skills/design/tournament_bracket/tech.md
@prompts/P2/P2-DS-数据源.md

请按 P2-DS 提示词正文执行需求拆解·数据源维度：
- 功能名：竞技场高级赛
- feature_root：案例/竞技场高级赛
- 功能缩写：ARENA
- skill_id：tournament_bracket
- 产出：案例/竞技场高级赛/02-需求拆解/竞技场高级赛/数据源/
- 先写 字段映射索引.md，登记全部 P-xx
请直接写入文件。
```

#### 6.4.3 对话示例：P2-R（规则维度）

```text
@案例/竞技场高级赛/01-原始策划案/竞技场高级赛/原始策划案.md
@案例/竞技场高级赛/02-需求拆解/竞技场高级赛/数据源/字段映射索引.md
@workflows/arena.workflow.json
@skills/design/tournament_bracket/design.md
@prompts/P2/P2-R-规则.md

请对「竞技场高级赛」原始策划案进行 P2-R 规则维度需求拆解：
- 功能缩写：ARENA
- 产出：案例/竞技场高级赛/02-需求拆解/竞技场高级赛/规则/
- L1 已有规则写「继承 tournament_bracket R-TB-xxx」，只写本项目 delta
- 每条 R- 须含伪代码、P-xx 依赖、来源 01 §x.x
请直接写入文件，按子系统拆多个 md。
```

#### 6.4.4 其余 P2 维度

复制对应 `prompts/P2/P2-*.md` 的「提示词正文」，替换占位符，@ 上表「必 @」列文件，**改本步任务与输出路径**即可。  
P2-EX ~ P2-T 的写法与 P2-R 相同，只是 Prompt 文件和产出子目录不同。

**P2 完成门禁**

## 8. 常见错误

| 错误 | 正确做法 |
|------|----------|
| 把 01 写在 `源文档/` | 01 定稿必须在 `产出/…/01-原始策划案/{功能名}/` |
| 02 写到 `templates/` | 只复制模板一次，产出写 `案例/` |
| 省略内层 `{功能名}` | 路径必须是 `02-需求拆解/{功能名}/规则/` |
| P2 @ docx 不转 01 | 先 P1-1 生成 `原始策划案.md` |
| 手改 `outputs/` | 改 02/03 后重新 `compile.py` |
| `feature_root` 与目录名不一致 | workflow 与 `产出/` 文件夹名对齐 |
| AI 跑管线时改 `skills/` | Skill 变更须维护者确认；业务只写 `产出/` |
| 新功能写到 `案例/` | 真实交付写 `产出/`；`案例/` 仅对照样例 |
| 未写 logs/ 执行日志 | 每次会话结束须 P5-4 → `logs/{YYYYMMDD}-{HHmmss}.log.md` |
| 一次对话跑完 P2 八维度 | 建议每步一个 Prompt，便于策划中途确认 |
| @ 整个产出文件夹 | 优先 @ 具体 md/json，避免上下文过大 |
| P3-2 在 P2 未完成时执行 | 须先完成 P2-DS 字段映射，否则 P-xx 不一致 |
