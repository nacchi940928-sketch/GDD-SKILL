## 1. 目录分工（不要混用）

| 目录 | 角色 | 谁写 | 是否进 Git |
|------|------|------|------------|
| **`源文档/`** | **仅原始 doc**（docx、ppt）；不含提取表 | 策划 | 可选 |
| **`templates/`** | **空模板**，新建时复制 | 维护者 | 是 |
| **`产出/{功能名}/`** | **管线交付物**（01~04 + logs + 看板） | 策划 + AI/程序 | 是 |
| **`案例/`** | **对照样例**（仅学习参考，如竞技场高级赛） | 维护者 | 是 |
| **`{feature_root}/开发文档/`** | `compile.py` **编译三包** | 工具 | 是（禁止手改） |
| **`workflows/*.json`** | 项目配置（`feature_root` 指向**产出**） | 程序/策划 | 是 |

**铁律**

- `源文档/` **只放原始 doc**，不放内嵌表、提取稿、配置表。
- **真实功能**的 01~04 必须在 `产出/{功能名}/`；docx 拆解备份在 `产出/…/01-…/源表提取/`。
- `案例/` 只放对照样例；新 docx 跑管线 → 建 `产出/{功能名}/`。

### 1.1 补充与修改看板

每个**产出**功能根目录应有 **`产出/{功能名}/补充与修改看板.md`**：

```text
产出/{功能名}/
├── README.md
├── 补充与修改看板.md          ← ★ 待补充/待修改总表
├── 04-待策划补充/{功能名}/
└── 03-…/待确认事项.md
```

示例：[产出/超级鸡马/补充与修改看板.md](产出/超级鸡马/补充与修改看板.md)  
对照样例（非产出）：[案例/竞技场高级赛/](案例/竞技场高级赛/)

## 2. 路径变量（Prompt 占位符）

执行 Prompt 前统一替换：

| 占位符 | 含义 | 填写说明 |
|--------|------|----------|
| `{功能名}` | 功能中文名，与**产出**子目录名一致 | 见 §9 |
| `{feature_root}` | **产出**根路径 | `产出/{功能名}` |
| `{功能缩写}` | 编号用英文缩写 | 如 `R-{缩写}-001` |
| `{skill_id}` | L1 框架 Skill id | workflow `selected_skills`；无 L1 则留空 |
| `{项目}` | workflow 文件名（不含 `.json`） | 如 `workflows/arena.workflow.json` → `arena` |

**标准阶段路径**（以下 `{功能名}` 两处必须相同）：

```text
{feature_root}/
├── 00-立项探索/{功能名}/          ← P0 可选
├── 01-原始策划案/{功能名}/
│   ├── 原始策划案.md              ← P1 定稿（P2+ 主读）
│   └── 源表提取/                  ← docx 内嵌表备份
├── 02-03需求拆解与功能点梳理/         ← ★ P2/P3 拆解真源
│   ├── 02-需求拆解.md           ← 策划/运营/产品/老板汇报
│   └── 03-功能点梳理.md         ← 程序/AI 主读；格式见竞技场 docx
├── 04-待策划补充/{功能名}/
├── 开发文档/                    ← compile 三包（勿手改）
├── logs/                          ← ★ 每次文档更新新建 {YYYYMMDD}-{HHmmss}.log.md
├── 补充与修改看板.md
└── README.md
```

**P2 八维度（写入 `{spec_root}/02-需求拆解.md` 单文件）**：

```text
规则 · 边界条件 · 红点 · 数据源 · UI交互 · 状态机 · 校验规则 · 验收标准
```

## 3. 原始策划案放哪里

```text
策划 docx / 口述
      ↓
源文档/{任意文件名}.docx          ← 源文件归档（可选）
      ↓ P1-1 或 P0-4
产出/{功能名}/01-原始策划案/{功能名}/
      ├── 原始策划案-草稿.md    ← P0-4 产出，策划审阅
      └── 原始策划案.md         ← P1 定稿，P2 拆解 @ 此文件
```

| 文件 | 阶段 | 能否进 P2 |
|------|------|-----------|
| `源文档/*.docx` | 输入 | 否（须先转 01） |
| `原始策划案-草稿.md` | P0-4 | 否（须 P1 定稿） |
| `原始策划案.md` | P1 定稿 | **是** |

**P2 及以后 @ 引用**：一律指向

```text
产出/{功能名}/01-原始策划案/{功能名}/原始策划案.md
```

不要 @ `源文档/` 下的 docx（除非 P1-1 转换步骤中临时使用）。

## 4. 各阶段：读什么、写什么

### P0 立项探索（可选）

| 步骤 | @ 引用 | 写出路径 |
|------|--------|----------|
| P0-1 | 策划口述 / `源文档/*` | `{feature_root}/00-立项探索/{功能名}/project.json` |
| P0-2 | `…/project.json` | `…/game_dna.json`、`game_dna.md` |
| P0-3 | game_dna + `skills/README.md` | `…/skill选型.md` |
| P0-4 | 上述 + L1 `design.md` | `…/玩法大纲.md`、`01-…/原始策划案-草稿.md` |

### P1 原始策划案

| 步骤 | @ 引用 | 写出路径 |
|------|--------|----------|
| P1-1 | `源文档/*.docx` 或 `原始策划案-草稿.md` | `{feature_root}/01-原始策划案/{功能名}/原始策划案.md` |
| P1-2 | `原始策划案.md` | `{feature_root}/01-原始策划案/{功能名}/完整性检查-gap清单.md` |

### P2 需求拆解（8 维度 → 单文档）

**前置 @**：`原始策划案.md` + `workflows/*.json` + L1 Skill（如有）

| 维度 | Prompt | 写入 02 章节 |
|------|--------|--------------|
| 数据源 | P2-DS | §6 数据概要 |
| 规则 | P2-R | §3 规则说明 |
| 边界条件 | P2-EX | §5 边界 |
| 状态机 | P2-SM | §2 状态机 |
| UI交互 | P2-UI | §4 UI |
| 红点 | P2-RD | §6.1 红点 |
| 校验规则 | P2-V | 默认跳过；V-xx → P3 附录 E.2 |
| 验收标准 | P2-T | §7 验收要点 |

**推荐顺序**：P2-DS → P2-R → P2-EX → P2-SM → P2-UI → P2-RD → P2-V → P2-T

**产出路径**：`{feature_root}/02-03需求拆解与功能点梳理/02-需求拆解.md`（单文件）

**写作规范**：[templates/02-需求拆解-写作规范.md](templates/02-需求拆解-写作规范.md)

**汇报主读**：`02-需求拆解.md` — 自然语言；**不含**伪代码、P-xx 大表、数据契约审计。

### P3 功能点梳理（程序可读）

| 步骤 | @ 引用 | 写出路径 |
|------|--------|----------|
| P3-1 | 01 + 02 | `03-功能点梳理.md` §0 |
| P3-2 | 01 + 02 | 各 `## N.` + **怎么实现（伪代码）** |
| P3-3 | 02 + 03 | 附录 A + **附录 D/E**（字段、审计、协议、配置表） |
| P3-4~5 | 03 | 附录 B/C |

**程序主读**：`03-功能点梳理.md` — 自包含，禁止「见 02」。

### 02 vs 03 内容边界

| 内容 | 02 | 03 |
|------|----|----|
| 规则 | R- 自然语言「规则说明」 | 伪代码 + P-xx 读写 |
| 流程 | 玩家阶段名 | Phase 枚举、状态机 |
| 数据 | §6 数据概要 | 附录 A/D/E |
| 验收 | T- 用户操作语言 | 附录 B 细场景 |

### P4~P6

| 阶段 | 主读 | 产出 |
|------|------|------|
| P4 | 01 + 02 + 03 | `{feature_root}/04-待策划补充/{功能名}/` |
| P5 | 02 + 03 + workflow | `{feature_root}/开发文档/程序包.md` 等 + **`logs/{时间}.log.md`** |
| P6 | 03 + `{feature_root}/开发文档/程序包.md` | server/client design 四件套（仓库外）；完成后**追加或新建** logs 条目 |

### 管线执行日志（每次文档更新必写）

**铁律**：只要本次会话改动了 `{feature_root}` 下任意交付文档，结束前**必须**新建一条日志——不限于跑完 P5 或全量管线。

| 触发场景 | 示例 |
|----------|------|
| 全量 / 部分管线 | P1~P6 任意组合执行完毕 |
| 单文档局部更新 | 改 `02-需求拆解.md` 某一章、补 R-xx |
| 04 回填回流 | 策划填 04 → Agent 回流 02/03 |
| 编译重跑 | 仅 `compile.py` 后仍须 log（记录 compile 与输入变更） |
| 目录 / 链接 / 规范维护 | 改 README、更新看板 |

写入路径：

```text
{feature_root}/logs/{YYYYMMDD}-{HHmmss}.log.md
```

| 规则 | 说明 |
|------|------|
| 命名 | **结束时刻**本地时间，如 `20260706-151530.log.md` |
| 频次 | 同功能多次更新 → **多条**日志并存，**禁止覆盖**已有 `.log.md` |
| 禁止 | 固定文件名（如 `管线执行报告.md`）、在旧 log 上追加、只口头说明不写文件 |
| 模板 | [templates/logs/模板.log.md](templates/logs/模板.log.md) |
| Prompt | [prompts/P5/P5-4-管线执行日志.md](prompts/P5/P5-4-管线执行日志.md)（名称保留；适用全部文档更新） |

**最小必填**（局部更新可省略未触达阶段）：

1. 元信息：**变更类型**、执行者、feature_root  
2. **本次变更文件清单**（路径列表，须与 git diff 可对齐）  
3. 到达节点 / 是否 compile / 阻塞项  
4. 下次建议起点  

全量管线时仍按模板填 P0~P6 阶段表；**仅改 02/03 一节**时阶段表未触达项标 `—`，但 §「本次变更」不可省略。

**README 索引**：`{feature_root}/README.md` 的「上次执行记录」链接指向**最新一条** log（按文件名时间排序）。

## 5. 新建功能（操作步骤）

### 5.1 初始化目录

```bash
# 在 GDD SKILL/ 下执行
功能名="你的功能名"
mkdir -p "产出/${功能名}/01-原始策划案/${功能名}"
mkdir -p "产出/${功能名}/02-需求拆解/${功能名}"
mkdir -p "产出/${功能名}/03-功能点梳理/${功能名}/功能点"
mkdir -p "产出/${功能名}/04-待策划补充/${功能名}"
mkdir -p "产出/${功能名}/logs"
# 若走 P0：
mkdir -p "产出/${功能名}/00-立项探索/${功能名}"
```

或复制模板：

```bash
cp -r templates/01-原始策划案/{功能名} "产出/${功能名}/01-原始策划案/${功能名}"
# 其余阶段同理
```

### 5.2 归档策划源文件

```text
源文档/你的策划案.docx   → 仅作输入，P1-1 @ 引用
```

### 5.3 创建 workflow

复制 `workflows/arena.workflow.json` → `workflows/{项目}.workflow.json`：

```json
{
  "feature_root": "产出/{功能名}",
  "selected_skills": ["resolution_standard", "interaction_feedback"],
  "skill_configs": { }
}
```

`feature_root` **必须**与 `产出/` 下文件夹名一致（不含末尾 `{功能名}` 子层）。

### 5.4 选路径

| 情况 | 路径 |
|------|------|
| 有 docx / 完整 01 | 跳过 P0 → P1-1 → P2 |
| 只有想法 | P0-1~4 → P1 定稿 → P2 |

### 5.5 编译

```bash
cd "GDD SKILL"
python tools/compile.py 产出/{功能名} --workflow workflows/{项目}.workflow.json
```

产出：`{feature_root}/开发文档/程序包.md | 测试包.md | 策划包.md`

## 6. 详细使用说明

本节说明**在 Cursor 里怎么 @ 文件、发什么消息、产出写到哪里**。  
所有路径相对于 `GDD SKILL/` 子项目根；对话里 @ 时用仓库内的真实路径。

### 6.1 三条上手路径

| 你的情况 | 从哪开始 | 目标 |
|----------|----------|------|
| **A. 有策划 docx** | §6.3 P1 → §6.4 P2 → §6.5 P3 | 最常见：docx → 01 → 02/03 |
| **B. 01 已定稿** | 直接 §6.4 P2 | 跳过 P1，做需求拆解 |
| **C. 只有想法** | P0-1~4 → P1 → P2 | 先立项再规格化 |

**核心原则**

- **@ 的是输入**（01、02、workflow、Prompt 规范）；**写的是输出**（`产出/{功能名}/` 下对应目录）。
- 一次对话建议只跑 **1 个 Prompt 步骤**（P3-2 可按章节分批）。
- 每步完成后**策划确认**，再进下一步；会话结束必做 **P5-4 写 logs**。

### 6.2 在 Cursor 里怎么 @

1. 在输入框输入 `@`，搜索文件名或文件夹。
2. **优先 @ 具体 `.md` / `.json`**，不要只 @ 整个 `案例/`（上下文过大易漏细节）。
3. 同时 @ **本步 Prompt 文件**（如 `prompts/P2/P2-R-规则.md`），让 Agent 按正文铁律执行。
4. 消息正文 = **替换占位符后的提示词正文** + 一句任务说明（见下文示例）。

**@ 引用写法示例**（Cursor 会自动补全路径）：

```text
@GDD SKILL/案例/竞技场高级赛/01-原始策划案/竞技场高级赛/原始策划案.md
@GDD SKILL/workflows/arena.workflow.json
@GDD SKILL/prompts/P2/P2-R-规则.md
```

### 6.3 阶段一：01 定稿（P1）

**何时做**：有 docx / 草稿，还没有 `原始策划案.md`，或 docx 有更新。

**@ 引用**

| 文件 | 路径 |
|------|------|
| 策划源（P1-1） | `源文档/{策划案}.docx` 或 `…/原始策划案-草稿.md` |
| Prompt | `prompts/P1/P1-1-Docx转原始案.md` |

**对话示例（P1-1）**

```text
@源文档/竞技场高级赛（纷乱的群殴锦标赛）活动优化.docx
@prompts/P1/P1-1-Docx转原始案.md

请按 P1-1 提示词正文执行：
- 功能名：竞技场高级赛
- feature_root：案例/竞技场高级赛
- 产出：案例/竞技场高级赛/01-原始策划案/竞技场高级赛/原始策划案.md
- 保留 docx 全部表格与章节，标注继承现网/新增/改动
请直接写入文件，不要只输出大纲。
```

**P1-2 完整性检查** — @ `原始策划案.md` + `prompts/P1/P1-2-完整性检查.md`  
产出：`01-…/完整性检查-gap清单.md`（只列 gap，不扩写 01）。

**门禁**：gap 清单无 P0 级阻塞 → 策划确认 01 → 进入 P2。

### 6.4 阶段二：需求拆解（P2 · 02）

**何时做**：`原始策划案.md` 已定稿，需要生成 **02-需求拆解**（8 维度、R-/P-/V- 编号）。

**固定顺序**（不可乱序）：

```text
P2-DS → P2-R → P2-EX → P2-SM → P2-UI → P2-RD → P2-V → P2-T
```

#### 6.4.1 各步 @ 引用速查

| 步骤 | 必 @ | 可选 @（有 L1 时） | 产出 |
|------|------|-------------------|------|
| **P2-DS** | `01/…/原始策划案.md`、`workflows/{项目}.workflow.json` | L1 meta/tech | `02-需求拆解.md` §6 |
| **P2-R** | 01 + `02-需求拆解.md` + workflow | L1 design.md | 02 §3 |
| **P2-EX** | 01 + 02 §3 | L1 design.md | 02 §5 |
| **P2-SM** | 01 + 02 §3 | L1 design/ux | 02 §2 |
| **P2-UI** | 01 + 02 §3 | L0 ux、tech | 02 §4 |
| **P2-RD** | 01 + 02 §4 | — | 02 §6.1 |
| **P2-V** | 01 + 02 + 03（若已有） | — | 03 附录 E.2 |
| **P2-T** | 01 + 02 已完成章节 | L1 qa.md | 02 §7 |

> **无 L1**：`skill_id` 留空；02 从 01 全量写。  
> **有 L1**：只写 delta，通用规则写「继承 {skill_id} R-xxx」。  
> **P-xx / 伪代码 / 审计**：P3 → `03-功能点梳理.md` 附录 A~E。

#### 6.4.2 对话示例：P2-DS（必须先做）

```text
@产出/超级鸡马/01-原始策划案/超级鸡马/原始策划案.md
@workflows/chickenhorse.workflow.json
@prompts/P2/P2-DS-数据源.md
@templates/02-需求拆解-写作规范.md

请按 P2-DS 执行：
- 功能名：超级鸡马
- feature_root：产出/超级鸡马
- 产出：02-需求拆解.md §6 数据概要（表名列表，不含 P-xx 大表）
请直接写入文件。
```

#### 6.4.3 对话示例：P2-R（规则维度）


## 8. 常见错误

| 错误 | 正确做法 |
|------|----------|
| 把 01 写在 `源文档/` | 01 定稿必须在 `产出/…/01-原始策划案/{功能名}/` |
| 02 写到 `templates/` | 只复制模板一次，产出写 `产出/` |
| 仍创建 `02-…/规则/` 多文件夹 | 写入 `02-需求拆解.md` 对应 § 章节 |
| P2 在 02 写伪代码 / P-xx | 02 仅自然语言；P3 → 03 附录 |
| P2 @ docx 不转 01 | 先 P1-1 生成 `原始策划案.md` |
| 手改 `{feature_root}/开发文档/` | 改 02/03 后重新 `compile.py` |
| `feature_root` 与目录名不一致 | workflow 与 `产出/` 文件夹名对齐 |
| AI 跑管线时改 `skills/` | Skill 变更须维护者确认；业务只写 `产出/` |
| 新功能写到 `案例/` | 真实交付写 `产出/`；`案例/` 仅对照样例 |
| 未写 logs/ 执行日志 | **每次更新** 01/02/03/04/看板/README 等交付文档后须 P5-4 **新建** log；禁止覆盖 |
| 一次对话跑完 P2 八维度 | 建议每步一个 Prompt，便于策划中途确认 |
| @ 整个产出文件夹 | 优先 @ 具体 md/json，避免上下文过大 |
| P3-2 在 P2 核心 R- 未完成时执行 | 须先完成 P2-R 规则说明，否则 03 缺业务输入 |
