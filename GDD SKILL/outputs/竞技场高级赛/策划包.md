竞技场高级赛（纷乱的群殴锦标赛）活动优化

1. 设计目的

1.1 竞技场锦标赛优化

设计目的： 在原有「纷乱的群殴」上，与 竞技场小组排名 衔接，自动划分 选手 / 观众；用 16 人淘汰赛 强化炫耀与竞争，用 竞猜 + 商店 让本期 持续可参与、有收益。

调整报名门槛，取消主动报名，按 联赛档位小组排名 自动入选。

优化参与条件，小组 前 4 为 参赛选手，其余为 观众。

新增竞猜系统，所有玩家通过竞猜玩法支持喜欢/熟悉的选手，强化归属感

新增商店系统，玩家持续参与该活动，可以兑换稀有道具

1.2 竞技场分组优化

设计目的：竞技场锦标赛需要依托竞技场分组，保证锦标赛 为 联赛前列玩家竞争 各个赛区的冠军；同时需要增加档位数量，激励更多玩家参与

不再使用同组最大鸟力差在20%的分组模式

使用定组插入的方式，按鸟力排序后将 各联赛档位 前列玩家，轮询分散到各周练小组，优先保护头部玩家在组内榜上的竞争体验与争第一空间，再填充其余席位。

增加档位数量

细分更多档位，让更多玩家体验到有“拿第一”的机会

2. 竞技场功能优化

2.1 竞技场分组优化

联赛档位优化

在当前基础上，增加更多的细分档位

※该优化为策划调整配置，需要美术资源补充

周练分组规则调整

按 鸟力 降序排序全体待分配玩家。

设当周已开启 / 将要填充的小组数为 G。

头部轮询入槽：排名第 1 的玩家进入 第 1 组，第 2 名进入 第 2 组 … 第 G 名进入 第 G 组（各组先占 1 个头部席位）。

余席填充：剩余玩家继续按排序 依次填充 各组，直至每组满 20 人 或待分配池耗尽（尾组可不足 20 人）。

定组插入：玩家在步骤完成后 固定 所属「XX 赛区 · 第 N 组」。

# 周练定组规则

> **L1 基底**: tournament_bracket（workflow: arena.workflow.json）
> **继承说明**: 见各条目标注「继承 R-TB-xxx」或「L2 delta」

> 废除旧「同组最大鸟力差≤20%」算法，改用头部轮询+余席填充。
> **仅服务端计算**，客户端只读 P-03 展示结果。
>
> **本文件全部为 L2 delta**（周练定组不在 L1 tournament_bracket 范围内，为竞技场高级赛前置子系统）

---

## R-001 废除旧算法

> **L2 delta**

**检测位置**: 服务端定组任务入口（每周定时触发）

**检测方式**: 切换为新算法实现，不再执行旧算法的鸟力差计算逻辑。旧代码分支标记为废弃（保留但不调用）。

**数据**: 无需读旧算法的鸟力差阈值配置。

---

## R-002 鸟力降序排序

> **L2 delta**

**触发**: 服务端每周定组任务启动。

**检测方式**: 
1. 查询本周需分组的所有玩家，取每人的鸟力值（字段 `【待程序补充】`）
2. 按鸟力降序排列，编号 1..N
3. 当周小组数 G 由当前已开启的小组数决定（从 P-03 统计）

**数据**:
| 读/写 | 数据 | 说明 |
|--------|------|------|
| 读 | 玩家鸟力 | `【待程序补充】` |
| 读 | 当前已开启小组数 G | 从 P-03 已存在的组名统计 |

---

## R-003 头部轮询

> **L2 delta**

**触发**: 排序完成后。

**检测方式**:
```
for i in 1..G:
    玩家[i] → 第 i 组
```
排名第 1 的玩家入第 1 组，第 2 入第 2 组…第 G 入第 G 组。每组此时各占 1 个头部席位。

**目的**: 保证头部玩家均匀分布在各组，避免强强集中。

**算例（G=3）**: 排名1→组1, 排名2→组2, 排名3→组3

---

## R-004 余席顺序填充

> **L2 delta**

**触发**: 头部轮询完成（G 个玩家已分配）。

**检测方式**:
```
for i in G+1..N:
    target_group = ((i - G - 1) % G) + 1  // 循环 1,2,3,...,G,1,2,3,...
    if 组[target_group].人数 < 20:
        玩家[i] → 组[target_group]
    else:
        跳过该组 // 该组已满
```
从第 G+1 名起，按名次依次循环填入各组。组满 20 人则跳过。

**算例（G=3）**: 
| 排名 | 入组 |
|------|------|
| 4 | 组1 |
| 5 | 组2 |
| 6 | 组3 |
| 7 | 组1（循环） |

---

## R-005 组人数上限

> **L2 delta**

**检测位置**: 每次填充时判断。

**检测方式**:
```
if 组[k].当前人数 >= 20:
    跳过该组，尝试下一组
```
服务端在填充循环中维护每组当前人数计数器。满 20 人的组不参与后续填充。

---

## R-006 末组可不足 20 人

> **L2 delta**

**触发**: 待分配池为空（所有玩家已分配）时停止。

**检测方式**:
```
if 已分配玩家数 == N:
    停止定组
```
不强制要求每组恰好 20 人。最后一组可能不足 20，这是正常状态。

---

## R-007 组名格式固定

> **L2 delta**

**触发**: 定组完成后写入。

**检测方式**:
```
P-03 = f"{联赛/赛区名} · 第 {k} 组"
```
组名写入 P-03，本周内不再变更。下周一重新定组时覆盖。

---

## R-008 客户端只读

> **L2 delta**

**客户端职责**: 
- 进入周练排行榜时拉取 P-03 展示组名
- **不参与**分组计算
- **不本地缓存**分组逻辑

**服务端职责**:
- 所有分组计算
- 写入 P-03 + P-06
- 定组完成后通知客户端刷新（可选：拉取或推送）

for m in [M1..M8]:

## L1 resolution_standard / tech

# 分辨率与适配 — 技术规范（L0 横切）

## 规范目标

全项目**唯一**画布与适配策略，防止多引擎/AI 实现乱拉伸、刘海遮挡、长屏错位。

## 设计稿 vs 实机

| 层 | 是否固定 9:20 |
|----|----------------|
| 设计稿 / 出图坐标 | ✅ 固定 `reference_resolution`（默认 1080×2340） |
| 实机屏幕 | ❌ 不固定 |

**核心**：固定 9:20 画布完整显示；更长屏宽度顶满、上下纯黑；更宽扁屏高度顶满、左右纯黑。

## 缩放模式（scale_mode）

| 模式 | 计算 | 适用 |
|------|------|------|
| **fit（默认）** | `scale = min(屏宽/1080, 屏高/2340)` | 固定画布，留纯黑边 |
| match_width | `scale = 屏宽/设计宽` | 备选 |
| match_height | `scale = 屏高/设计高` | 备选 |

X/Y **必须用同一 scale**，禁止 `scaleX ≠ scaleY`。

## 画布内布局（layout_anchor_policy）

默认 **stretch_center**：HUD 贴顶、Tab 贴底、中间 Fill。**不**向实机黑边区延伸。

| UI 区域 | 实机行为 |
|---------|----------|
| 顶部 HUD | 随画布 scale，不拉高 |
| 底部 Tab | 随画布 scale，不拉高 |
| 主玩法/列表 | 在 2340 内分配 |
| 居中弹窗 | 画布内居中，尺寸随 scale |
| 黑边区 | 纯黑、不可点 |

## 双层结构

- **背景层**：可铺满物理屏
- **交互层**：必须在 SafeArea 内

## 禁止

- 实机长屏中间向下延伸玩法区
- 4:3 挤扁中间不留黑边
- 黑边区放可点击按钮
- 非等比拉伸

## 验收标准

- [ ] 所有 UI 按设计坐标 1080×2340 出稿
- [ ] fit 模式下黑边不可点击
- [ ] 各系统 ux.md 不重复定义分辨率，只引用本文

## L1 tournament_bracket / design

# 锦标赛对阵树 — 设计规范（L1 基底）

## 规范目标

定义**单败淘汰赛对阵树**的通用策划规则，适用于「周练定组 → 自动/手动报名 → 签位 → 多轮战斗 → 结算」类活动。

L2 项目实例（如竞技场高级赛）**只写与本文不同的 delta**，相同规则标注「继承 tournament_bracket」。

## 适用范围

- 16/8/32 人单败 Bracket（由 `bracket_size` 配置）
- 选手 vs 观众双身份分流
- 服务端权威阶段驱动 + 客户端门控
- 可选竞猜子系统（`enable_betting=true` 时启用，规则见项目 delta）

## 玩家流程

```text
[活动入口] → [活动展示/公示]
  ├── 选手 → [决斗/战斗界面]
  └── 观众 → [对阵树界面] →（可选）竞猜
```

## 核心规则

### R-TB-001 报名模式

| registration_mode | 行为 |
|-------------------|------|
| `auto` | 定时任务触发，无主动报名 UI/接口 |
| `manual` | 玩家主动报名，有截止时间与资格校验 |

**自动报名（默认）**：
- 触发：`registration_cron`（如周一 UTC0）
- 读：玩家分组归属 + 组内排名
- 写：身份（选手/观众）、对阵树快照
- 失败：整事务回滚，签位与报名原子提交

### R-TB-002 身份判定

```
if rank in [1 .. contestant_top_n]:
    role = CONTESTANT
else:
    role = SPECTATOR
```

- 身份在 `identity_lock_days` 内不变（除非 GM 审计修改）
- 下一周期重新报名时覆盖

### R-TB-003 赛区/Bracket 组成

- 每 `groups_per_bracket` 个来源组合并为一个独立 Bracket
- 各 Bracket 独立淘汰赛、独立冠军、独立竞猜池（若启用）
- 规模：`bracket_size` 叶节点选手 + 对应观众池

### R-TB-004 签位生成

- Bracket 签位表**固定**（不可随机），由配置或常量表定义
- 报名成功后生成签位 → 写叶节点 → `robot_fill=true` 时不足补机器人
- 签位失败回滚报名事务

### R-TB-005 对战与晋级

- 单败：胜者写入父节点 slotLeft/slotRight
- 轮次顺序：R16 → QF → SF → FINAL（随 `bracket_size` 缩放）
- **继承现网战斗模块**的项目：只写对接点，不重写战斗判定逻辑

### R-TB-006 阶段日程

由 `phase_schedule` 实例化，典型结构：

| 阶段 | 选手 | 观众 |
|------|------|------|
| ANNOUNCE（公示） | 预览对阵，不可战斗 | 预览，不可竞猜 |
| BATTLE_n（各轮） | 可战斗 | 可竞猜（若启用） |
| SETTLE（结算） | 发奖、积分转化 | 同左 |

每日 UTC0（或可配置 tick）切换阶段；服务端权威，客户端读倒计时 + 本地门控。

## 数据模型（策划视角）

| 概念 | 说明 |
|------|------|
| BracketSnapshot | 完整对阵树，含所有节点 |
| BracketNode | matchId, round, slotLeft/Right, winnerId, status |
| PlayerRole | CONTESTANT / SPECTATOR |
| Phase | ANNOUNCE / BATTLE_* / SETTLE |

字段编号 P-xx 在 L2 `02/数据源/字段映射索引.md` 登记，L1 不绑定具体 P 编号。

## 边界与异常

| 编号 | 场景 | 处理 |
|------|------|------|
| EX-TB-001 | 定时任务失败 | 需 L2 定义重试策略 |
| EX-TB-002 | 签位生成失败 | 回滚报名，告警 |
| EX-TB-003 | 战斗超时未结算 | 需 L2 定义超时判负/延期 |
| PRE-TB-001 | 玩家未在来源组 | 不参与本期 |
| LIM-TB-001 | 身份锁定期内 | 不因游戏内事件改变身份 |

## 验收标准

- [ ] 自动/手动报名与 `registration_mode` 一致
- [ ] 身份判定符合 `contestant_top_n`，锁定期内不变
- [ ] 签位固定、机器人补位符合 `robot_fill`
- [ ] 阶段切换服务端权威，客户端门控与阶段一致
- [ ] 节点状态 PENDING → IN_PROGRESS → COMPLETED 无歧义
- [ ] L2 delta 与 workflow `skill_configs` 数值一致

# 锦标赛对阵树 — 技术规范（L1 基底）

## 服务 / 模块

| 模块 | 职责 |
|------|------|
| TournamentScheduler | 阶段切换定时任务 |
| RegistrationService | 自动/手动报名 |
| BracketService | 签位生成、晋级写入 |
| MatchService | 对战调度（可继承现网） |
| BettingService | 竞猜（optional） |
| PushGateway | PhaseChange / BracketUpdate |

## 数据结构 — BracketNode（骨架）

```json
{
  "matchId": 0,
  "round": 1,
  "matchIndex": 0,
  "slotLeft": 0,
  "slotRight": 0,
  "winnerId": 0,
  "status": "PENDING",
  "isRobotLeft": false,
  "isRobotRight": false,
  "scoreLeft": 0,
  "scoreRight": 0,
  "parentMatchId": 0
}
```

**status 枚举**：`PENDING` | `IN_PROGRESS` | `COMPLETED`

**round 映射**（bracket_size=16）：1=R16, 2=QF, 3=SF, 4=FINAL

| 接口 | 方向 | 说明 |

| PhaseChangePush | S→C | 阶段变更 |
| BracketUpdatePush | S→C | 节点状态/胜者更新 |

L2 在 `02/数据源/协议/` 展开完整 proto/message。

## 实现约束

- 签位生成与报名同一事务
- 阶段切换前校验上一轮全部 COMPLETED（或 L2 定义例外）
