# PromptMerge 规划 — GDD Skill × Vibe Studio 融合

> 分支：`promptmerge`  
> 目标：同一套**可复用基底** + **项目/功能差异化配置**，降低策划重复劳动，提升程序可读性与 AI 管线可执行性。

---

## 1. 两套体系对比

| 维度 | GDD SKILL（当前） | Vibe Studio V5 Lite |
|------|-------------------|---------------------|
| 定位 | 单功能从原始案 → 程序可执行规格 | 多 Skill 知识包 → 多职能编译产出 |
| 粒度 | 按**功能**（如竞技场高级赛） | 按**系统 Skill**（如 shop_system） |
| 复用 | templates/ 模板 + 案例 | skills/ 知识包 + config_schema |
| 程序主读 | `03-功能点梳理/`（自包含） | `06_Feature_Spec.md`（编译产出） |
| 策划主读 | `01-原始策划案` + `02-需求拆解` | `design.md` + workflow 节点配置 |
| 差异化配置 | `04-待策划补充` 回填 | `skill_configs` in workflow.json |
| 强项 | 规则编号、P-xx 字段、伪代码、8 维度拆解 | 职能分轨、依赖解析、横切 Skill、编译一致性 |
| 弱项 | 每功能重复写 8 维度；无跨项目基底 | Feature 层偏薄；缺 P-xx / 伪代码约定 |

**结论**：GDD SKILL 的 **02/03 执行深度** + V5 Lite 的 **Skill 复用 + 项目配置** 应合并，而非二选一。

---

## 2. 目标架构（三层基底）

```text
┌─────────────────────────────────────────────────────────┐
│  L0 横切基底（全项目共用，极少改）                          │
│  resolution / interaction_feedback / save / qa_baseline │
│  → 对应 V5: skills/tech|ux|qa/*                           │
└─────────────────────────────────────────────────────────┘
                            ↓ 引用
┌─────────────────────────────────────────────────────────┐
│  L1 系统基底（跨功能复用，按系统类型）                       │
│  tournament_bracket / shop / currency / sign_in / …     │
│  → 对应 V5: design.md + meta.config_schema              │
│  → 对应 GDD: templates/02-需求拆解 各维度**骨架**          │
└─────────────────────────────────────────────────────────┘
                            ↓ 实例化
┌─────────────────────────────────────────────────────────┐
│  L2 项目/功能实例（本项目取值 + 规则差异）                   │
│  workflow.skill_configs + 案例/02-需求拆解 + 03-功能点     │
│  → 04-待策划补充 只填「相对基底的 delta」                    │
└─────────────────────────────────────────────────────────┘
```

**原则**：
- L0/L1 写一次，多项目编译/复制
- L2 只写**与基底不同的部分**（数值、文案、特殊规则）
- `03-功能点梳理` 仍是程序 AI 管线的**唯一主读文档**

## 3. 映射关系（V5 Skill ↔ GDD 阶段）

| V5 知识包文件 | GDD SKILL 对应 | 说明 |
|---------------|----------------|------|
| `meta.md` | 功能元数据 + `04/02-配置数值` schema | id、依赖、可配置项 |
| `design.md` | `01-原始策划案` + `02/规则` + `02/边界条件` | 策划规则叙述 |
| `ux.md` | `02/UI交互` + `02/状态机`(客户端) | 界面架构、状态机 |
| `tech.md` | `02/数据源` + `02/校验规则` | 协议、字段、校验 |
| `qa.md` | `02/验收标准` + `03/验收场景` | 测试用例 |
| `feature.md` | `03-功能点梳理/功能点/*` | 程序任务拆解 |
| workflow `skill_configs` | `04-待策划补充/02-配置数值` | 项目实例参数 |

## 4. 执行层：提示词 vs Skill

| 类型 | 位置 | 用途 |
|------|------|------|
| **提示词** | `prompts/P2/P2-*.md` | 复制「提示词正文」到 Agent 对话，直接执行 |
| **Skill** | `skills/gdd/p2-decompose/SKILL.md` | 维度规范、格式示例、铁律（Agent 可读，人不逐条粘贴） |
| **L1 基底** | `skills/design/*` 等 | 跨项目可复用系统知识 |

以下按**管线阶段**组织；P2 八个维度已落地为 `prompts/P2/`，P0/P3+ 仍见下文参考话术。

---

### P0 — 立项与边界（来自 V5 Discovery + GameDNA）

**P0-1 项目发现**
```text
按 Project Discovery Agent 向我提问，一次只问一组：
项目名称 / 一句话描述 / 参考游戏 / 目标平台 / 目标用户 / 商业模式。
只输出 project JSON，不要生成 GDD，不要展开系统细节。
```

**P0-2 GameDNA 定调**
```text
根据已确认的 project JSON，提炼 game_dna：
fantasy / emotion / core_experience / core_loop / excluded_systems。
参考游戏仅作启发，信息不足标「待研究」，禁止编造规则数值。
输出 game_dna JSON，不要写具体功能设计。
```

**P0-3 功能层级与选型**
```text
根据 game_dna，列出本功能属于哪一层：
基础功能层 / 边缘系统层 / 核心玩法层 / 活动玩法层。
从 skills/ 或 templates/ 已有基底中推荐可复用的系统模板；
库中没有的列「待建 Skill 清单」，不要虚构 id。
```

---

### P1 — 原始案整理（GDD 阶段 01）

**P1-1 Docx → 原始策划案**
```text
输入：策划 .docx 或 .md
输出：01-原始策划案/{功能名}/原始策划案.md

要求：
- 用 XML 顺序提取 docx（禁止 paragraphs/tables 分离）
- 覆盖：概述 → 功能流程 → 规则 → UI交互 → 美术 → 配置结构
- 自然语言叙述，保留设计意图，不强行表格化
- 标注「继承现网」与「本次新增」的边界
```

**P1-2 原始案完整性检查**
```text
对照 01 模板检查清单，列出缺失章节与待确认项。
不补写内容，只输出 gap 列表供策划确认。
```

---

### P2 — 需求拆解（GDD 阶段 02，8 维度）

**通用前缀（每个维度 Prompt 都要带）**
```text
输入：01-原始策划案 +（如有）L1 系统基底文档
输出：02-需求拆解/{功能名}/{维度}/
铁律：
- 每条有唯一编号，标注来源章节
- 展开到可实现：检测位置 / 检测方式 / 数据依赖 / 伪代码
- 与 L1 基底相同的规则写「继承 {skill_id}」，只写 delta
- 禁止「见原始文档」式模糊引用
```

| Prompt ID | 维度 | 输出编号 | 核心要求 |
|-----------|------|----------|----------|
| P2-R | 规则/ | R-xxx | 触发条件 + 行为 + 伪代码 + P-xx 依赖 |
| P2-EX | 边界条件/ | EX-/PRE-/LIM- | 异常/前置/限制 + 检测层 + 处理逻辑 |
| P2-RD | 红点/ | RD-xxx | 触发/消除/检测/层级聚合 |
| P2-DS | 数据源/ | P-xx | 配置表/协议/枚举/字段映射索引 |
| P2-UI | UI交互/ | — | 跳转图 + 每界面布局/交互/空态 |
| P2-SM | 状态机/ | — | 状态转移表 + 服务端/客户端伪代码 |
| P2-V | 校验规则/ | V-xxx | 校验逻辑 + 错误码 + 防篡改 |
| P2-T | 验收标准/ | T-/B-/E- | 正常/边界/异常 + 前置 + 验证点 |

**P2-DS 字段映射（关键）**
```text
为所有运行时/配置/协议字段分配 P-xx 编号。
在 数据源/字段映射索引.md 登记：编号 / 含义 / 类型 / 来源表或协议 / 读写方。
禁止在后续文档自创未登记字段名。
```

**P2-SM 状态机（V6 可执行写法）**
```text
每个状态写清：
- 触发条件 / 表现 / 禁止 / 验收（含自动化可检查项）
服务端、客户端分别给伪代码块。
参考 V6：Disabled 不仅要「置灰」，还要写 pointer-events 与禁止行为。
```

---

### P3 — 功能点梳理（GDD 阶段 03，程序主文档）

**P3-1 阅读说明生成**
```text
输出 0-阅读说明.md，包含：
- 文档约定（自包含铁律）
- 功能点导航表
- 名词定义
- 全局行为矩阵（如 选手 vs 观众）
- 界面跳转图
- 继承现网规则摘要
```

**P3-2 功能点拆分**
```text
按原始案顶级章节 → 功能点/*.md，每个文件必须含标准块：
涉及模块 → 功能点 → 数据来源(P-xx) → 怎么实现(通用/服务端/客户端) → 程序分工

铁律（来自转换规范）：
- 绝对自包含，禁止「见原始文档」
- 表格完整：涉及模块表、数据来源表、程序分工表
- 禁止概括性删减，保留全部业务细节
- 每条验收项自带关键规则
```

**P3-3 功能点 → Feature Spec 对齐**
```text
将 03/功能点/* 映射为 feature.md 任务清单：
| 优先级 | 功能 | 依赖 | 验收 | 对应 03 文件 |
用于 V5 Compiler 产出 06_Feature_Spec.md，但 03 仍为程序 AI 主读。
```

**P3-4 待确认事项提取**
```text
扫描 01-03，输出 待确认事项.md，分三类：
待程序确认 / 待策划确认 / 待美术确认
每条注明：位置、问题、建议默认值、阻塞级别。
```

---

### P4 — 待策划补充（GDD 阶段 04）

**P4-0 增量补充原则**
```text
对比 L1 系统基底，04 各文件只填与基底不同的项。
基底已定义的字段命名/GM/打点模板写「沿用 {skill_id}」。
```

| Prompt ID | 文件 | 填写者 |
|-----------|------|--------|
| P4-01 | 01-字段命名.md | 程序确认 P-xx → 代码名 |
| P4-02 | 02-配置数值.md | 策划填最终值 |
| P4-03 | 03-UI文案.md | 策划 |
| P4-04 | 04-GM需求.md | 策划+程序 |
| P4-05 | 05-打点需求.md | 策划 |
| P4-06 | 06-美术资源.md | 策划+美术 |
| P4-07 | 07-本地化.md | 策划 |
| P4-08 | 08-新手引导.md | 策划 |

---

### P5 — 编译与验收（V5 Compiler 风格）

**P5-1 职能分轨检查**
```text
检查文档是否错轨：
- 交互视觉细节不应堆在 规则/ 或 01
- 协议字段不应散落在 UI交互/
- 测试用例应对齐 验收标准/ 与 验收场景.md
输出错轨清单与建议移动目标。
```

**P5-2 一致性编译（人工或脚本）**
```text
输入：02 全维度 + 03 + workflow.skill_configs
输出：
- 程序包：03-功能点梳理/（主读）+ 04 已填项
- 测试包：验收标准 + 验收场景 + qa 基底
- 策划包：01 + 02/规则摘要 + 节点配置
禁止手改 outputs/；变更回流到 02/03/04 或 L1 Skill。
```

**P5-3 策划验收清单**
```text
- [ ] 03 可独立开发，无外部跳转依赖
- [ ] P-xx 全部登记且 04-01 已确认命名
- [ ] 状态机无歧义，含服务端/客户端伪代码
- [ ] excluded_systems / 继承现网 边界清晰
- [ ] skill_configs 与 02/规则 数值一致
```

---

### P6 — 开发管线（对接内容要点中的 AI 自动开发）

**P6-1 后端管线编排**
```text
输入：03-功能点梳理 + 02/数据源 + 02/校验规则 + 02/状态机(服务端)
输出：server/design/{功能}/ 需求文档 + 设计方案 + 开发方案 + 管线编排
按功能点顺序排列任务，标注协议(P-xx)与配置表依赖。
```

**P6-2 前端管线编排**
```text
输入：03 + 02/UI交互 + 02/状态机(客户端) + 02/红点 + server 已交付协议
输出：client/design/{功能}/ 同上四件套
引用 resolution_standard / interaction_feedback 横切基底，不重复定义。
```

**P6-3 增量开发（继承现网）**
```text
标记「继承现网」的功能点：
- 03 中只写 delta 与对接点
- 程序分工表注明：复用模块 / 改动模块 / 新增模块
- 禁止对继承模块重写完整规格
```

---

### P7 — Bug 修复回流

**P7-1 Bug → 异常分析**
```text
输入：Bug 报告 + 日志 + 当前 03/02 相关章节
输出：异常分析文档（现象 / 复现 / 根因假设 / 影响范围）
不直接改代码，先对照 P-xx 与状态机找文档缺口。
```

**P7-2 需求调整 → 重走管线**
```text
确定根因后，标注需改的维度（规则/状态机/边界/…），
仅重跑受影响的 P2/P3 Prompt，更新 04 待确认项，再进入 P6 管线。
```
